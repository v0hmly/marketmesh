# API

Каталог содержит исходные protobuf-схемы, конфигурацию EasyP и инструменты генерации. Go-код генерируется в `backend/api/gen/go/`, TypeScript — в `frontend/gen/`. Исходные схемы отделяют публичные ConnectRPC-контракты от внутренних gRPC-контрактов и протокола обратного туннеля.

Сгенерированные файлы не редактируются вручную и не коммитятся: они перечислены в `.gitignore`. Ручные `go.mod`, `go.sum`, `package.json` и README остаются в Git.

Пакет `backend/api/tunnel/v1` выполняет общий строгий разбор и структурную проверку кадров туннеля перед обработкой в `gateway-in` или `gateway-out`. Состояние потока, проверка согласованных возможностей, deadline относительно текущего времени и независимый allowlist маршрутов остаются обязанностью реализаций gateway.

## Инструменты и команды

Единственная конфигурация protobuf workflow находится в `api/easyp.yaml`. EasyP запускает только локальные плагины: схемы не отправляются в публичный сервис генерации. Точные версии CLI, `protoc` и плагинов зафиксированы в `api/tools/protobuf-versions.env`. Управляемые репозиторием исполняемые файлы хранятся в игнорируемом корневом `bin`, а архивы загрузок, protobuf-зависимости и временные результаты — в `.cache/protobuf`.

```bash
task api:bootstrap       # установить зафиксированные инструменты
task api:deps            # скачать зависимости по api/easyp.lock
task api:lint            # проверить схемы
task api:generate        # обновить Go и TypeScript код
task api:breaking        # сравнить v1-контракты с dev
task api:generate-check  # сравнить две чистые генерации побайтово
task api:self-test       # проверить плагины и отрицательные сценарии
task api:verify          # выполнить все API-проверки
```

`task api:deps:update` используется только при осознанном изменении зависимости в `api/easyp.yaml`; изменившийся `api/easyp.lock` должен входить в тот же pull request. EasyP 0.16.1 разрешает breaking reference только как локальную ветку, поэтому перед проверкой локальная `dev` должна быть обновлена из `origin/dev`.

`task api:self-test` создаёт временный v1-контракт вне дерева исходников и подтверждает, что повторная генерация совпадает побайтово, некорректное имя поля отклоняется lint, а удаление поля обнаруживается breaking check.

После клонирования `task generate` создаёт API-код и CSS дизайн-токенов.
Go-задачи и команды frontend workspace генерируют контракты до
компиляции; для прямого `go test`, IDE или `pnpm --filter …` сначала выполните
`task generate`. Нужны Go из `backend/go.work`, Node/pnpm из `frontend/package.json`.
При первом запуске инструменты и зависимости скачиваются; версии не меняются.
Повторная генерация удаляет устаревшие protobuf-файлы, сохраняя ручные manifests.

`task dev:up` генерирует API внутри Docker и не требует Node/pnpm на хосте.
Dockerfile с API используют одинаковый stage `api-generated`: генераторы работают
внутри сборки из `.proto`, закреплённых версий и lock-файлов. BuildKit переиспользует
этот stage; при изменении набора pnpm-пакетов обновляйте его COPY manifests во всех
таких Dockerfile. Локальные generated-файлы исключены также через `.dockerignore`,
поэтому ручной `docker build` из чистого checkout не требует `task generate` на хосте.
Toolchain и Node не попадают из этого stage в runtime-образы.

`api:generate-check` не требует уже созданных результатов и не изменяет их:
сравниваются две независимые генерации во временных каталогах. Проверка layout
отклоняет возвращение generated-файлов в индекс Git; сборка и тесты проверяют
совместимость свежих результатов с потребителями. Историю Git не переписываем —
старые версии содержат прежние артефакты.


Изолированная Go-проверка (`backend/tools/go-workspace.sh isolated`) сначала
генерирует API, затем выполняет test/build каждого модуля с `GOWORK=off` и
`-mod=readonly`. Временный `-modfile` подставляет только текущий `api/gen/go`:
его код больше не публикуется через исходники Git. Остальные зависимости берутся
из закреплённых версий; зарегистрированные `go.mod`/`go.sum` остаются неизменны.
Это позволяет проверять добавочные поля контракта в том же PR, что и их потребителя.
