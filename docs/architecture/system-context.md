# Системный контекст и границы доверия

## Цель документа

Документ определяет участников, внешние зависимости, зоны доверия и допустимые направления соединений. Он отвечает на вопрос «кто с кем может устанавливать соединение», а не заменяет схему развёртывания или правила межсетевого экрана.

## Участники

| Участник | Цель | Начальный уровень доверия |
| --- | --- | --- |
| Покупатель | Просматривать каталог, управлять учётной записью, оформлять заказ, получать уведомления, использовать чат | Недоверенный внешний субъект |
| Сотрудник | Выполнять разрешённые административные и операционные действия | Аутентифицированный субъект без неявных прав |
| Оператор платформы | Развёртывать и диагностировать систему | Привилегированный субъект с обязательным аудитом |
| Внешний поставщик | Доставка, платёж, почта или иная будущая интеграция | Недоверенная внешняя система |
| Рабочая нагрузка | Выполнять функцию конкретного сервиса | Доверие только после проверки уникальной машинной идентичности |

## Зоны

| Зона | Содержимое | Допустимые входящие соединения | Допустимые исходящие соединения |
| --- | --- | --- | --- |
| Интернет | Браузеры и внешние системы | Не контролируются проектом | Только к опубликованным адресам DMZ |
| DMZ | Пограничный API, realtime, сервер туннеля, пограничный Redis, публичные и карантинные объекты | TLS из интернета; mTLS от внутреннего ретранслятора | Интернет для строго разрешённых интеграций; внутри DMZ; без новых соединений во внутреннюю зону |
| Внутренняя | Ретранслятор, доменные сервисы, БД, внутренний Redis, NATS, исходное объектное хранилище | Только от внутренних рабочих нагрузок и через плоскость административного доступа | Внутри зоны; исходящий mTLS к серверу туннеля; явно разрешённые внешние зависимости |
| Административная плоскость | VPN, прокси доступа или бастион, аудит | От управляемых устройств и проверенных сотрудников | Только к разрешённым административным интерфейсам |

## Инварианты межзонального взаимодействия

- Маршрутизация и правила межсетевого экрана не разрешают DMZ начинать TCP-соединение во внутреннюю зону.
- Внутренний ретранслятор начинает mTLS-соединение к известному серверу туннеля в DMZ.
- Двунаправленный поток не отменяет границу доверия: каждый входящий логический запрос считается данными из DMZ.
- В туннеле отсутствуют поля для произвольного адреса, порта и полного имени gRPC-метода.
- Разрешение метода выполняется независимо на сервере туннеля и внутреннем ретрансляторе.
- Сервисная идентичность привязана к сертификату рабочей нагрузки, а не к IP-адресу.
- Административные интерфейсы не публикуются через пользовательский пограничный API.

## Контекстная схема

~~~mermaid
flowchart TB
    browser[Браузер покупателя]
    staff[Устройство сотрудника]
    external[Внешние поставщики]

    shop[Публичный контур магазина в DMZ]
    core[Внутреннее ядро магазина]
    admin[Плоскость административного доступа]

    browser -->|TLS: ConnectRPC, WS, SSE| shop
    shop -->|ответы и события| browser
    staff -->|VPN и сильная аутентификация| admin
    admin -->|ограниченные операции и аудит| core
    core -->|исходящий mTLS-туннель| shop
    core -->|явно разрешённые вызовы| external
    external -->|подписанные webhook-вызовы в отдельные точки DMZ| shop
~~~

## Данные и владельцы

| Категория | Владелец | Допустимое присутствие в DMZ |
| --- | --- | --- |
| Парольные хэши, MFA, ключи восстановления | Сервис аутентификации | Запрещено |
| Внешние пользовательские сессии | Сервис аутентификации | Только непрозрачный cookie у клиента и минимальный псевдонимный контекст в пограничном Redis |
| Внутренние утверждения о сессии | Сервис аутентификации выдаёт, целевой сервис проверяет | Запрещено хранить; не должно возвращаться браузеру |
| Профиль и адреса | Сервис пользователей | Запрещено кэшировать без отдельного решения |
| Счётчики ограничений | Пограничная платформа | Разрешено |
| Публичные производные изображений | Медиаподсистема | Разрешено после проверки и публикации |
| Исходные загрузки | Медиаподсистема | Только временно в карантине |
| Доменные события | Сервис-владелец события | Не передаются в DMZ без отдельного преобразования в публичное событие |

## Базовые пользовательские сценарии

### Публичное чтение

Пограничный API может ответить из явно разрешённого кэша. При промахе запрос проходит через туннель в целевой сервис. Ответ кэшируется только при явной политике метода и без персональных данных.

### Операция с авторизацией

Пограничный API не разбирает пользовательский токен как источник полномочий. Сервис аутентификации подтверждает сессию и создаёт ограниченное утверждение для целевого сервиса. Доменный сервис принимает решение по своим правам и данным.

### Долгоживущее соединение

WebSocket или SSE завершается в DMZ. Внутренние события передаются через отдельный класс туннельного трафика. Переподключение клиента, пропуски и повторная доставка обрабатываются явным протоколом, а не удержанием внутреннего соединения на каждый браузер.

## Не входит в текущий контекст

- Платёжный провайдер, доставка, каталог, заказ и склад будут добавлены отдельными решениями.
- Региональная отказоустойчивость и аварийное восстановление пока не определены.
- Конкретный поставщик PKI и система управления секретами выбираются при проектировании платформы.
- Числовые SLO, лимиты и сроки хранения будут зафиксированы после появления измеримого профиля нагрузки.
