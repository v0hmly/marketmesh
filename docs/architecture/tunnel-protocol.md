# Проект протокола обратного туннеля

## Статус документа

Документ синхронизирован с контрактом v1 из [`api/proto/tunnel/v1/tunnel.proto`](../../api/proto/tunnel/v1/tunnel.proto). Wire-схема, абсолютные числовые пределы и структурная валидация зафиксированы задачей MM-10. Стратегия балансировки, рабочие пределы конкретного маршрута и состояние потока уточняются в реализациях `gateway-in` и `gateway-out`, но не могут ослабить абсолютные пределы v1.

## Цели

- передавать разрешённые запросы из DMZ во внутренние сервисы без соединений, инициированных из DMZ;
- поддерживать обычные RPC, серверные события и двунаправленные сообщения чата;
- обеспечивать отмену, дедлайны, обратное давление и ограничение ресурсов;
- аутентифицировать обе стороны соединения;
- не раскрывать DMZ адреса, порты и топологию внутренних сервисов;
- позволять независимо масштабировать обычный и realtime-трафик.

## Не цели

- универсальный TCP-, HTTP- или SOCKS-прокси;
- перенос произвольного gRPC-метода по имени, полученному от клиента;
- замена авторизации в доменных сервисах;
- гарантия «ровно один раз»;
- долговременное хранение событий;
- распространение внешнего пользовательского токена во внутренние сервисы.

## Установление соединения

1. Внутренний ретранслятор разрешает адрес сервера туннеля из доверенной конфигурации.
2. Он устанавливает TLS-соединение из внутренней зоны в DMZ.
3. Стороны взаимно проверяют короткоживущие сертификаты рабочей нагрузки, цепочку доверия и назначение имени.
4. Ретранслятор вызывает `tunnel.v1.TunnelService/Connect` и первым отправляет `ConnectRequest` с `GatewayOutHello`: 16-байтовый instance ID, список версий, capability, классы трафика, RouteId и локальные receive-пределы.
5. Сервер возвращает `ConnectResponse` с `GatewayInHello`, назначает 16-байтовый tunnel ID и выбирает ровно версию 1. Отсутствие версии 1 или неизвестные значения завершают соединение до передачи прикладных запросов.
6. Обе стороны обмениваются служебными сообщениями живости. Служебный механизм не заменяет TCP keepalive и настройки gRPC keepalive.

Одно соединение не является единицей высокой доступности. Каждый экземпляр ретранслятора поддерживает несколько потоков, а сервер туннеля видит несколько экземпляров.

## Модель кадров

Направления типизированы разными protobuf-оболочками. Клиент gRPC `gateway-out` отправляет `ConnectRequest`, а сервер `gateway-in` — `ConnectResponse`. Это не позволяет стороне DMZ отправить `Result` или `RevokeSession`, а внутренней стороне — открыть произвольный новый запрос.

| Тип кадра | internal → DMZ | DMZ → internal | Назначение |
| --- | --- | --- | --- |
| Hello | да | да | Согласование версии, возможностей, маршрутов и пределов |
| Open | нет | да | Открытие логического запроса по разрешённому RouteId |
| Data | да | да | Часть запроса, ответа или realtime-сообщения |
| HalfClose | да | да | Завершение передачи одной стороной |
| Cancel | да | да | Отмена логического запроса с конечной причиной |
| Result | да | нет | Итоговый безопасный код и завершающие метаданные |
| Credit | да | да | Разрешение передать дополнительный объём Data |
| Ping / Pong | да | да | Контроль живости прикладного потока |
| Drain | да | да | Прекращение новых запросов до абсолютного deadline |
| RevokeSession | да | нет | Закрытие связанных внешних WS/SSE-соединений |

`FrameHeader` содержит protocol version, tunnel ID, request ID, sequence и traffic class. Hello использует версию 0 только как оболочку negotiation; после Hello разрешена только версия 1. Tunnel ID, request ID, instance ID и session ID имеют ровно 16 байт. Прикладной кадр имеет положительный sequence; tunnel-level кадр имеет нулевой sequence и пустой request ID.

`Open.deadline` и `Drain.deadline` являются абсолютными `google.protobuf.Timestamp` в UTC. `Cancel` — отдельный oneof frame type, поэтому он не может одновременно быть `Open` или `Data`. Строгий декодер дополнительно отвергает wire-кадр, в котором закодировано несколько известных oneof payload.

## Версия и неизвестные данные

Декодер v1 работает fail-closed:

- до protobuf unmarshal проверяется абсолютный размер и наличие ровно одного header и одного payload;
- неизвестный top-level tag считается неизвестным frame type;
- неизвестные поля отклоняются рекурсивно, а не молча отбрасываются;
- неизвестные числовые значения enum RouteId, TrafficClass, Capability, MetadataKey и кодов отклоняются;
- версия, отличная от 1 после handshake, отклоняется;
- ошибки разбора не содержат исходный кадр, metadata или payload.

Расширение полей внутри v1 допустимо по protobuf breaking policy, но начинает использоваться только после отдельного согласования capability или следующей версии протокола. Старый peer вправе закрыть туннель при встрече неизвестного поля: соединение не расширяет полномочия автоматически.

## Сопоставление методов

Публичный маршрут описывается в версионируемом реестре:

| Поле политики | Пример смысла |
| --- | --- |
| Идентификатор маршрута | Стабильное числовое или перечислимое значение |
| Целевой сервис и метод | Локальная конфигурация ретранслятора |
| Тип обмена | Одиночный, серверный поток, двунаправленный поток |
| Требование сессии | Публичный, сессия, повышенная аутентификация |
| Максимальный размер | Предел запроса и ответа |
| Максимальный дедлайн | Верхняя граница времени |
| Класс трафика | Управление, обычный RPC, realtime |
| Политика повтора | Запрещён, безопасен, требует ключ идемпотентности |

Реестр компилируется или подписывается как часть поставки. Сервер туннеля проверяет публичную политику, а ретранслятор независимо проверяет внутреннюю копию. Расхождение приводит к отказу, а не к расширению доступа.

В v1 зарезервирован следующий конечный набор RouteId:

| RouteId | Число | Класс |
| --- | ---: | --- |
| `AUTH_REGISTER_CREDENTIALS` | 1 | control/auth |
| `AUTH_LOGIN` | 2 | control/auth |
| `AUTH_REFRESH_SESSION` | 3 | control/auth |
| `AUTH_REVOKE_SESSION` | 4 | control/auth |
| `AUTH_SESSION_ASSERTION` | 5 | control/auth |
| `USER_GET_ME` | 100 | regular |
| `USER_UPDATE_ME` | 101 | regular |
| `REALTIME_CHAT` | 200 | realtime |
| `REALTIME_NOTIFICATIONS` | 201 | realtime |

Число определяет только публичную семантику. Адрес, порт и полное имя внутреннего gRPC-метода находятся в локальном статическом реестре `gateway-out` и отсутствуют в wire-контракте.

## Метаданные

Имя metadata представлено enum, а не строкой. В v1 разрешены только:

| MetadataKey | Ограничение |
| --- | --- |
| `CONTENT_TYPE` | ровно `application/protobuf`, не более 64 байт |
| `TRACEPARENT` | W3C version 00, 55 ASCII-символов, ненулевые trace/span ID |
| `TRACESTATE` | печатный ASCII без пустых элементов, не более 512 байт |
| `SESSION_ASSERTION` | непрозрачное подписанное внутреннее утверждение, не более 16 KiB, только в Open |

Deadline и idempotency key имеют отдельные поля `Open`, request ID — отдельное поле header. Пользовательские `Authorization`, `Cookie`, `Host`, `Forwarded`, `X-Forwarded-*` и произвольные имена передать невозможно. Неизвестный MetadataKey, пустое значение, дубликат ключа или session assertion в `Result` считаются нарушением протокола.

## Классы трафика

| Класс | Назначение | Особенность |
| --- | --- | --- |
| Управление и аутентификация | Проверка сессии, отзыв, служебные операции | Зарезервированная ёмкость и строгие пределы |
| Обычный RPC | Короткие запросы доменных сервисов | Справедливое распределение и дедлайны |
| Realtime | WS, SSE и чат | Отдельные потоки, квоты соединений и обратное давление |

Классы используют отдельные очереди и предпочтительно отдельные gRPC-потоки. Переполнение realtime не должно блокировать проверку сессии или обычный RPC.

## Управление потоком и ресурсами

Абсолютные пределы v1:

| Ресурс | Предел |
| --- | ---: |
| Закодированный protobuf-кадр | 1 MiB |
| `Data.payload` | 256 KiB |
| Собранное логическое сообщение | 8 MiB |
| Активные логические запросы на туннель | 4096 |
| Metadata на кадр | 16 записей |
| Одно metadata value | 16 KiB |
| Один Credit increment | 1 MiB |
| Idempotency key | 128 байт |
| RouteId в Hello | 64 |
| Версии в Hello | 8 |
| `Result.retry_after` | 5 минут |

Hello может предложить меньшие receive-пределы. Эффективное значение не превышает минимум двух сторон и абсолютный предел v1. `max_frame_bytes` обязан быть больше `max_data_bytes`, а `max_message_bytes` — не меньше `max_data_bytes`.

- очередь каждого класса и каждого клиента ограничена;
- количество одновременных логических запросов ограничено на туннель, экземпляр, маршрут и псевдонимного пользователя;
- Data передаётся только при наличии кредитов принимающей стороны;
- размер кадра и общий размер сообщения проверяются на обеих сторонах;
- логический запрос всегда имеет дедлайн, не превышающий максимум маршрута;
- отмена распространяется к целевому gRPC-вызову;
- медленный получатель отключается или теряет допускающие потерю события согласно политике канала;
- память не должна расти пропорционально числу ожидающих браузеров без заданного верхнего предела.

Нативное управление потоком HTTP/2 необходимо, но недостаточно: нужны прикладные квоты, иначе один логический поток может занять общую ёмкость.

## Повторы и идемпотентность

Туннель не повторяет изменяющий запрос автоматически, если маршрут не объявлен безопасным. Клиент передаёт ключ идемпотентности для операций, допускающих повтор после разрыва. Целевой сервис хранит результат или факт обработки в своей границе данных.

После переподключения незавершённый запрос считается завершившимся с неопределённым результатом. Пограничный компонент решает вопрос повтора по политике маршрута. Для realtime используется отдельный курсор или последовательность событий, а не повтор кадров старого туннеля.

## Ошибки

Внутренний gRPC-код преобразуется в enum `ResultCode`: OK, INVALID_ARGUMENT, UNAUTHENTICATED, PERMISSION_DENIED, NOT_FOUND, CONFLICT, RESOURCE_EXHAUSTED, DEADLINE_EXCEEDED, CANCELED, UNAVAILABLE или INTERNAL. В `Result` нет свободного текстового сообщения. Адрес сервиса, имя экземпляра, стек, SQL, внутреннее имя метода и детали политики остаются только в защищённой телеметрии, связанной по request ID.

Ошибки протокола разделяются на:

- ошибку одного логического запроса;
- исчерпание квоты класса;
- несовместимость или нарушение туннеля;
- недоступность внутреннего назначения.

Неверный кадр не должен приводить к панике процесса. Повторяющиеся нарушения закрывают туннель и создают событие безопасности.

## Высокая доступность и обслуживание

- сервер туннеля принимает трафик только при наличии подходящего готового ретранслятора;
- readiness ретранслятора означает готовность туннеля и критических внутренних зависимостей, а не только работающий процесс;
- балансировка учитывает класс трафика, поддерживаемые маршруты и текущую нагрузку;
- Drain запрещает новые логические запросы, но даёт ограниченное время завершить активные;
- переподключение использует экспоненциальную задержку с разбросом и верхней границей;
- идентификатор экземпляра не используется как долговременная пользовательская идентичность.

## Безопасность

- TLS не ниже принятой платформой безопасной версии; сертификаты ротируются автоматически;
- обе стороны проверяют уникальную машинную идентичность и назначение сертификата;
- набор доверенных центров и отзыв обновляются без остановки всей системы;
- список методов строится по принципу запрета по умолчанию;
- внутреннее утверждение проверяет целевой сервис, даже если ретранслятор уже проверил форму;
- конфигурация не содержит общего секрета для всех экземпляров;
- тела и секретные метаданные не попадают в обычные журналы;
- аномалии по методам, размерам и отказам политики наблюдаемы.

## Наблюдаемость

Минимальные метрики: число активных туннелей, время переподключения, активные запросы по классу, глубина очереди, объём кадров, задержка, отмены, дедлайны, отказы списка разрешений, ошибки проверки сертификатов и число отброшенных realtime-событий.

Трасса внешнего запроса продолжается через туннель с безопасным контекстом трассировки. Идентификаторы трассы не предоставляют полномочий.

## Проверки перед первой эксплуатацией

1. Невозможно указать произвольный адрес, порт или метод.
2. Неизвестный тип, поле, enum или версия кадра безопасно отклоняются.
3. Просроченный запрос не достигает доменного сервиса.
4. Отмена освобождает очередь, память и внутренний вызов.
5. Переполнение realtime не ухудшает зарезервированную ёмкость аутентификации.
6. Разрыв туннеля не вызывает автоматический повтор изменяющего запроса.
7. Отозванный сертификат перестаёт создавать новые туннели.
8. Секреты и тела не появляются в логах и метриках.
9. Drain завершает обслуживание без бесконечного ожидания.
10. Нагрузочный тест подтверждает заданные пределы памяти и числа горутин.

## Открытые эксплуатационные параметры

- число gRPC-потоков на экземпляр в пределах общего resource budget;
- меньшие рабочие лимиты отдельных маршрутов и окружений;
- конкретные значения keepalive, максимальных route deadline и задержек переподключения;
- алгоритм выбора ретранслятора;
- срок хранения ключей идемпотентности;
- семантика восстановления пропущенных уведомлений и сообщений чата.
