# Обзор архитектуры

## Назначение

Проект — образовательный монорепозиторий онлайн-магазина на Go и Vue. Архитектура должна позволять начать с небольшого локального окружения, но не закреплять решения, которые делают небезопасным или чрезмерно дорогим последующее масштабирование.

Первая серверная версия включает сервисы аутентификации и пользователей, публичный пограничный шлюз, внутренний ретранслятор, PostgreSQL, Redis, NATS JetStream и SeaweedFS. Клиент взаимодействует с системой через ConnectRPC, WebSocket и SSE.

## Основные принципы

1. Сеть считается недоверенной независимо от зоны. Доступ в VPN не означает автоматического доверия пользователю или рабочей нагрузке.
2. Из DMZ нельзя инициировать сетевое соединение во внутреннюю зону. Межзональный прикладной обмен проходит по обратному туннелю, который открывает внутренний ретранслятор.
3. Обратный туннель не является произвольным TCP-прокси. Он передаёт только явно разрешённые типы сообщений и RPC-методы.
4. Внешняя пользовательская сессия известна только сервису аутентификации. Остальные сервисы получают короткоживущее утверждение о сессии с ограниченной аудиторией.
5. Каждый сервис владеет своими данными. Межсервисные изменения передаются событиями с гарантией доставки «как минимум один раз» и идемпотентной обработкой.
6. Компоненты DMZ не хранят исходные пользовательские токены, внутренние утверждения, пароли и профильные персональные данные.
7. Наблюдаемость, ограничение ресурсов, отзыв доступа и ротация ключей проектируются одновременно с основным потоком запросов.

## Логическая схема

~~~mermaid
flowchart LR
    user[Пользовательский браузер]
    employee[Сотрудник]
    access[Прокси административного доступа]

    subgraph dmz[DMZ]
        edge_api[Пограничный API]
        edge_rt[Пограничный realtime]
        tunnel_server[Сервер туннеля]
        edge_redis[(Пограничный Redis)]
        public_media[(Публичные и карантинные объекты)]
    end

    subgraph internal[Внутренняя зона]
        relay[Внутренний ретранслятор]
        auth[Сервис аутентификации]
        users[Сервис пользователей]
        auth_db[(БД аутентификации)]
        users_db[(БД пользователей)]
        auth_redis[(Внутренний Redis аутентификации)]
        nats[(NATS JetStream)]
        source_media[(Исходные объекты SeaweedFS)]
    end

    user -->|ConnectRPC, WebSocket, SSE| edge_api
    user -->|WebSocket, SSE| edge_rt
    edge_api --> edge_redis
    edge_rt --> edge_redis
    edge_api --> tunnel_server
    edge_rt --> tunnel_server

    relay -->|исходящий mTLS, двунаправленный gRPC-поток| tunnel_server
    relay -->|внутренний gRPC| auth
    relay -->|внутренний gRPC| users
    auth --> auth_db
    auth --> auth_redis
    users --> users_db
    auth --> nats
    users --> nats

    source_media -->|публикация безопасных производных| public_media
    public_media -->|исходящее извлечение из карантина| source_media

    employee -->|VPN и проверка личности| access
    access -->|разрешённые административные действия| internal
~~~

Стрелка ретранслятора к серверу туннеля показывает направление установления соединения. После установления двунаправленный поток переносит разрешённые запросы из DMZ во внутренние сервисы и ответы обратно.

## Компоненты

### DMZ

- Пограничный API завершает TLS, принимает ConnectRPC, применяет первичные ограничения и нормализует внешний запрос.
- Пограничный realtime завершает WebSocket и SSE, управляет внешними соединениями и преобразует события в кадры публичных протоколов.
- Сервер туннеля сопоставляет запросы с доступными внутренними ретрансляторами. Он не выбирает произвольный адрес или порт.
- Пограничный Redis хранит счётчики ограничений, безопасные публичные кэши и минимальный псевдонимный контекст сессии.
- Публичное объектное хранилище содержит только опубликованные производные, а карантин — ещё не проверенные загрузки.

Роли пограничного API, realtime и сервера туннеля разделены логически и могут сначала поставляться одним исполняемым файлом. У них должны оставаться отдельные конфигурации, метрики и возможность независимого масштабирования.

### Внутренняя зона

- Внутренний ретранслятор устанавливает исходящие mTLS-соединения в DMZ и является точкой принудительного применения межзональной политики.
- Сервис аутентификации владеет учётными данными, внешними сессиями, MFA, ключами подписи, обменом токенов и отзывом сессий.
- Сервис пользователей владеет профилем, настройками, адресами, метаданными аватара и другими профильными персональными данными.
- NATS JetStream доставляет доменные события. Транзакционный outbox связывает изменение данных с публикацией события.
- Внутренний SeaweedFS хранит исходные и обработанные объекты, не доступные из DMZ напрямую.

### Плоскость административного доступа

Административный доступ является отдельной логической плоскостью. Сотрудник подключается через VPN, но затем проходит проверку личности и политики в прокси доступа или бастионе. Для операций применяются минимальные права, аудит и, по возможности, выдача доступа на ограниченное время.

## Основные потоки

### Обычный RPC-запрос

1. Браузер отправляет ConnectRPC-запрос в DMZ.
2. Пограничный API проверяет протокол, размер, лимиты и допустимость публичного метода.
3. Если требуется пользовательский контекст, пограничный компонент получает у сервиса аутентификации короткоживущий контекст через туннель.
4. Сервер туннеля передаёт запрос по уже установленному внутренним ретранслятором потоку.
5. Ретранслятор повторно проверяет метод, метаданные, дедлайн и размер, затем вызывает внутренний gRPC-сервис.
6. Ответ и нормализованная ошибка возвращаются тем же логическим каналом.

### Вход и дальнейшая авторизация

1. Сервис аутентификации создаёт непрозрачную внешнюю сессию и устанавливает защищённый cookie.
2. Для пограничных ограничений выдаётся минимальный псевдонимный контекст без персональных данных.
3. Для вызова конкретного внутреннего сервиса сервис аутентификации подписывает короткоживущее утверждение с нужной аудиторией.
4. Получатель проверяет подпись, срок, издателя, аудиторию и тип утверждения локально по опубликованным ключам.
5. При выходе или отзыве сессии очищаются связанные кэши и закрываются активные WebSocket/SSE-соединения.

### Регистрация пользователя

1. Сервис аутентификации сохраняет учётную запись и запись outbox в одной транзакции.
2. Из outbox публикуется событие регистрации личности.
3. Сервис пользователей идемпотентно создаёт профиль с тем же неизменяемым идентификатором субъекта.
4. Повторная доставка события не создаёт второй профиль.

### Загрузка пользовательского файла

1. Файл попадает в карантинное хранилище DMZ по ограниченной одноразовой операции.
2. Внутренний обработчик сам извлекает объект из DMZ, проверяет тип, размер и вредоносное содержимое.
3. Исходник и безопасные производные сохраняются во внутреннем хранилище.
4. Только явно разрешённые производные публикуются обратно в публичное хранилище DMZ.

## Развёртывание

Для локальной разработки Docker Compose и Kubernetes в OrbStack имитируют разные зоны отдельными сетями, пространствами имён, политиками сети и раздельными экземплярами Redis/SeaweedFS. В рабочей среде DMZ и внутренняя зона должны быть разделены сетями или кластерами с внешне проверяемыми правилами межсетевого экрана.

Локальная имитация удобна для разработки, но не считается доказательством реальной сетевой изоляции.
