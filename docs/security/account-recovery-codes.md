# Резервные коды Auth (MM-91)

В настройках безопасности аккаунта с включённым подтверждением входа можно
создать восемь одноразовых резервных кодов. Генерация требует активного сеанса,
текущего пароля и шестизначного кода из письма. В dev письма доставляет локальный
Mailpit. Резервный код заменяет только второй шаг входа: пароль обязателен.

Каждый код содержит 128 случайных битов и показан один раз после фиксации
транзакции. Формат — четыре группы по восемь шестнадцатеричных символов; при входе
допускаются верхний регистр, отсутствие дефисов и пробелы по краям. Коды не
отправляются письмом и не сохраняются в browser storage, журнале сессии или
телеметрии. Письмо сообщает о замене набора и ведёт в настройки безопасности.
Ответы API имеют `Cache-Control: no-store`. Интерфейс очищает секреты при уходе,
смене владельца или состояния сеанса. Копирование и хранение кодов пользователь
выполняет самостоятельно.

## Хранение и атомарность

Миграция Auth `000005_recovery_codes` добавляет таблицу HMAC-SHA-256 отпечатков,
связанных с subject и revision учётных данных. Используется отдельный домен HMAC
`recovery-code-v1`; исходный секрет не попадает даже в зашифрованный mail outbox.
Новый набор целиком заменяет предыдущий. Проверка подтверждения, замена набора,
погашение challenge и уведомление фиксируются одной транзакцией PostgreSQL RW.

Вход сериализуется блокировкой credential владельца. Погашение резервного кода,
погашение password-approved login challenge, создание сессии и уведомление о
входе атомарны. При сбое записи сессии или письма код остаётся доступен. При потере
ответа после commit либо сбое активации в Redis код остаётся погашенным: сервер
не может безопасно определить, получил ли клиент результат. Повторная генерация
также не раскрывает уже выданный набор. UI не повторяет такие запросы автоматически.

Revision отзывает набор при сбросе/смене пароля, начале/подтверждении/отмене смены
почты, изменении подтверждения входа и переходах удаления аккаунта. Старые
отпечатки больше не принимаются; следующий набор физически заменяет их. Обычный
выход из сеанса не отменяет резервные коды. Удаление данных владельца входит в MM-92.

## Ограничения и поставка

- Проверка резервных кодов: до пяти попыток на subject за 15 минут, включая
  успешные. Новая login challenge или повторная отправка письма лимит не сбрасывает.
- Генерация использует общий лимит проверки текущего пароля, интервал отправки
  письма не менее минуты, до пяти писем и 15 проверок email-кода за 10 минут.
- Подтверждение генерации действует 10 минут. После трёх неверных email-кодов
  код перевыпускается; после исчерпания бюджета требуется подождать.
- GetCredentials возвращает только число оставшихся кодов. Повторного чтения
  секретов нет. При утрате набора создайте новый через пароль и письмо.
- Миграция применяется до новых экземпляров Auth, затем обновляются Auth и оба
  gateway, затем storefront. Старые экземпляры игнорируют новую таблицу и
  продолжают требовать email-код; резервный вход станет доступен после обновления.
- Откат приложения сохраняет email 2FA. Перед down-миграцией остановить трафик
  резервных кодов и вернуть старые экземпляры. Down безвозвратно отзывает наборы.

## Проверки

PostgreSQL integration проверяет гонку 16 разных login challenges за один код,
чужой subject, неверный purpose, повторное раскрытие, общий бюджет, rollback
сессии/outbox, замену набора, ревокацию паролем и запрет legacy bypass. Browser E2E
проходит через HTTPS, оба gateway, реальный Auth, PostgreSQL/Redis и Mailpit:
генерация, однократный вход, замена, отсутствие секретов в storage/письме, потеря
ответа и axe. Снимки экрана, trace и video для этих тестов выключены.
