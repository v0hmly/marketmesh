# Почта и безопасность аккаунта Auth (MM-90)

Покупатель регистрируется по почте и подтверждает её перед первым входом.
При включённом подтверждении входа одного пароля недостаточно: `StartLogin`
выдаёт challenge, а `CompleteLogin` принимает одноразовый шестизначный код.
Без этой настройки `StartLogin` сразу устанавливает cookie. Старый `Login`
не позволяет обойти включённый код. Почтовый код не является защитой от фишинга.

Storefront меняет пароль, почту и настройку кода и управляет собственными сеансами в
разделах «Вход и безопасность» и «Сеансы и устройства» MarketMesh ID
(`/account/id#security`; адрес `/account/security` из писем ведёт туда же, MM-97).
Страницы `/account/security/verify`, `reset`, `change_email`, `cancel_email` завершают
действия из писем. Bearer-token
находится во fragment ссылки, сразу удаляется из адреса и остаётся только в памяти
страницы. Действие подтверждается кнопкой; открытие ссылки само по себе ничего
не меняет. Пароли, коды и ссылки не попадают в Web Storage, события аналитики,
логи SMTP или публичные сведения об ошибке.

## Сроки и ограничения

| Действие | Правило |
| --- | --- |
| Подтверждение почты | Одноразовая ссылка на 24 часа |
| Восстановление пароля, смена/отмена почты | Одноразовая ссылка на 30 минут |
| Код входа/настройки | 10 минут с создания challenge, срок не продлевается при переотправке |
| Повторная отправка | Не чаще раза в минуту; до 5 писем и 15 проверок за 10 минут на аккаунт и назначение |
| Ошибки кода | После 3 ошибок перевыпуск; после исчерпания — новый вход после завершения бюджета |
| Ошибки пароля | 5 попыток за 15 минут; отдельный общий бюджет повторной проверки пароля для защищённых изменений |
| Отзыв других сеансов | Через 24 часа после создания текущего сеанса; собственный текущий сеанс можно закрыть сразу |

Защитное окно сейчас относится к **каждому новому сеансу**. Признак знакомого
устройства не собирается. Письмо о входе отправляется при каждом новом входе;
неизвестные IP, браузер и местоположение так и обозначаются.

Смена пароля, подтверждение новой почты и переключение кода закрывают **все**
сеансы владельца, включая текущий. Настройка кода и запрос смены почты требуют
текущий пароль; переключение кода дополнительно подтверждается письмом.
Отмена смены почты аннулирует ещё не использованную ссылку подтверждения.
После уже подтверждённой смены старая ссылка отмены недействительна.

Регистрация и запрос ссылки возвращают нейтральный ответ о существовании адреса.
Профиль User создаётся через прежний registration outbox. Блокировки, изменение
учётных данных, расходование challenge, выпуск/отзыв сессий и запись письма
фиксируются в транзакции PostgreSQL под блокировкой аккаунта. Digest кода — HMAC;
ссылка содержит случайный 256-битный секрет. Обязательный повтор запроса после
неизвестного результата записи отсутствует: UI требует проверить состояние.

## Время в письмах (MM-95)

Письма со ссылкой или кодом показывают длительность **с момента запроса** и точный
дедлайн: «Ссылка действует 24 часа с момента запроса. Подтвердите почту до
24 сентября 2026, 11:32 (UTC+3)». HTML и текстовая версия содержат одинаковые сведения.
Уведомления безопасности используют тот же формат времени события.

Storefront передаёт IANA-пояс браузера (`Intl.DateTimeFormat().resolvedOptions().timeZone`)
в `X-MarketMesh-Time-Zone` только для Auth на своём origin. Gateway переносит
метаданные через private `BrowserContext`; Auth проверяет имя и сохраняет пояс
в зашифрованном payload очереди. Это недоверенная настройка отображения конкретного
запроса, а не признак владельца или постоянная настройка аккаунта. Восстановление
пароля использует пояс браузера, запросившего письмо. Геолокация по IP не применяется.

Пустой, неизвестный, повторённый или некорректный пояс даёт явный `(UTC)`.
Транспорт по-прежнему отклоняет недопустимые управляющие символы и превышение
лимита 128 байт. Auth содержит `time/tzdata`: системная база часовых поясов в
минимальном контейнере не требуется. Смещение вычисляется для времени события
или дедлайна, включая переход на летнее время и дробные смещения.

Дедлайн проверяется сервером в UTC и не меняется. Повтор SMTP сохраняет исходное
время запроса; перевыпуск кода показывает оставшуюся длительность challenge,
не обещая новые 10 минут. В письме нет статических «завтра» и «осталось»:
они устаревают при позднем открытии. После недействительной/истёкшей ссылки
подтверждения почты или сброса пароля страница предлагает «Получить новую ссылку»
и форму почты без автоматической отправки; для смены почты ведёт в настройки.

Миграция БД не нужна: новое поле JSON необязательно. Старые ожидающие письма
отображаются в UTC, старый Auth игнорирует новое поле payload. Добавочное поле
protobuf позволяет последовательное обновление gateway/Auth; старый gateway
временно не передаст пояс. Для полного UX обновляются оба сервиса и storefront.
Откат на совместимую предыдущую версию возвращает UTC, сохраняя ключ очереди,
ссылки и их сроки. Обновление tzdata — вместе с обновлением Go/Auth.

## Runtime и локальный Mailpit

В текущем dev используется только [Mailpit account-local](../../infra/account-local/README.md).
Внешняя доставка не настроена. Нужны миграции Auth 000001–000004 и параметры:

| Переменная | Назначение |
| --- | --- |
| `AUTH_EMAIL_ENABLED=true` | Включает исполняемые сценарии и mail worker |
| `AUTH_SESSIONS_ENABLED=true` | Cookie-сессии PostgreSQL/Redis |
| `AUTH_REGISTRATION_EVENTS_ENABLED=true` | Атомарный outbox регистрации |
| `AUTH_EMAIL_KEY_FILE` | Абсолютный путь к постоянному случайному ключу из 32 байт, права 0600 |
| `AUTH_EMAIL_PUBLIC_ORIGIN` | Точный HTTPS origin из `AUTH_ALLOWED_ORIGINS`; ссылки строятся только из него |
| `AUTH_EMAIL_DOMAIN` | Почтовый домен отправителя, по умолчанию `marketmesh.test` |
| `AUTH_SMTP_ADDRESS` | В локальном стенде `mailpit:1025` |
| `AUTH_SMTP_PLAINTEXT_REASON` | Явная причина изолированного локального plaintext SMTP; допустим только в development/test без SMTP credentials |
| `AUTH_SMTP_USERNAME`, `AUTH_SMTP_PASSWORD` | Опциональные учётные данные relay; в Mailpit не используются |

Без локального исключения SMTP требует STARTTLS с проверкой сертификата и TLS1.3.
Время одной доставки ограничено 10 секундами. Почтовый worker берёт до 20 писем
между тиками в одну секунду; один worker доставляет последовательно. После ошибки
письмо ожидает от 2 до 256 секунд, максимум 12 попыток и не дольше собственного
срока. SMTP 5xx завершает доставку без повтора. Потеря ответа после DATA может
привести к дубликату: Message-ID стабилен, код/ссылка остаются одноразовыми.

Payload outbox зашифрован AES-GCM с отдельным производным ключом и привязкой к ID
письма. При успешной доставке, истечении или окончательном отказе payload очищается;
техническая запись хранится 7 дней. Lease 30 секунд защищает завершение чужим
worker. Ключ должен переживать рестарт и быть одинаковым на всех экземплярах Auth.
Его нельзя молча пересоздать: потеряются ожидающие письма и действующие challenge.

## Развёртывание и откат

Миграция добавочная, но включённую проверку почты/кода нельзя откатить на старый
password-only binary. Если схема 000004 уже присутствует, текущий Auth отказывается
стартовать с `AUTH_EMAIL_ENABLED=false`. Сначала миграция и ключ, затем обновление
всех Auth и шлюзов с новыми typed routes; storefront — после готовности backend.
Смешанный старый/new Auth за одним балансировщиком во время включения не допускается.

Обычный откат — остановить приём новых входов и вернуть совместимую версию MM-90,
сохранив ключ и таблицы. Down-миграция допустима только для одноразовой тестовой БД
либо отдельного согласованного восстановления с отзывом сессий и остановкой Auth.

Резервные коды реализуются в MM-91, удаление аккаунта с исполнением срока и
очисткой Auth/User/Files — в MM-92. MM-90 не показывает неработающие действия.
Расширенные поля профиля — MM-93, аватар — MM-65.
