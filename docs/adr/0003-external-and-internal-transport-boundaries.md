# ADR-0003: Границы внешних и внутренних транспортов

- Статус: Принято
- Дата: 2026-08-31
- Авторы: команда проекта
- Заменяет: нет
- Заменено решением: нет

## Контекст

Браузеру нужны короткие RPC-запросы, двунаправленный чат и однонаправленные уведомления. Внутренним Go-сервисам нужны строгие контракты, эффективная передача и единые перехватчики. Публикация внутренних gRPC-сервисов напрямую раскрыла бы топологию и связала внешний контракт с внутренним.

## Решение

Использовать три внешних транспорта:

- ConnectRPC поверх HTTPS для обычных запросов браузера;
- WebSocket для чата и сценариев с двунаправленными сообщениями;
- SSE для однонаправленных пользовательских уведомлений.

Все внешние соединения завершаются в DMZ. Внутри зоны сервисы взаимодействуют по gRPC. Запросы из DMZ проходят через прикладной обратный туннель, после чего внутренний ретранслятор вызывает целевой gRPC-метод.

Пограничный слой делится на логические роли:

- пограничный API для ConnectRPC;
- пограничный realtime для WebSocket и SSE;
- сервер туннеля для связи с внутренними ретрансляторами.

На старте роли могут находиться в одном Go-исполняемом файле, но должны иметь отдельную конфигурацию, обработчики, метрики и возможность последующего раздельного развёртывания.

Публичные контракты определяются отдельно от внутренних. Отображение публичного маршрута во внутренний метод является явным и версионируемым. Ошибки нормализуются: браузер не получает имя внутреннего сервиса, адрес экземпляра, стек или внутренние метаданные.

WebSocket и SSE не создают выделенное внутреннее сетевое соединение на каждый браузер. Пограничный realtime мультиплексирует подписки и получает события через отдельный класс туннельного трафика.

## Рассмотренные альтернативы

### Только REST/JSON

Прост и универсален, но не даёт единого строго типизированного контракта с внутренним gRPC и не решает realtime.

### Публичный нативный gRPC

Эффективен, но поддержка браузером требует дополнительных транспортных допущений и сильнее связывает внешний и внутренний контракты.

### Только WebSocket

Один транспорт выглядит проще, но требует заново определять запрос-ответ, кэширование, дедлайны, ошибки и восстановление для обычных операций.

### Только SSE для чата и уведомлений

SSE подходит для серверных уведомлений, но клиентские сообщения чата всё равно потребуют отдельного HTTP-канала и иной семантики.

## Последствия

### Положительные

- Каждый внешний сценарий использует подходящую модель транспорта.
- Внутренние сервисы сохраняют единый gRPC-контракт.
- Внутренняя топология и служебные ошибки скрыты от браузера.
- Роли можно масштабировать по разному профилю нагрузки.

### Отрицательные и риски

- Нужно сопровождать три внешних протокола и их общую модель авторизации.
- Преобразование ошибок и потоков может потерять семантику без контрактных тестов.
- Долгоживущие соединения требуют отдельного управления лимитами и развёртыванием.
- Один стартовый бинарник может скрыть нежелательную связанность ролей.

## Защитные и эксплуатационные требования

- TLS завершается только в контролируемой точке DMZ.
- Origin для WebSocket и правила CORS проверяются явно.
- Для SSE отключается нежелательное буферизование прокси и задаётся heartbeat.
- Все запросы имеют предел размера; RPC имеют дедлайн, WS/SSE — предел соединений и бездействия.
- Публичная схема не содержит внутренних имён и закрытых полей.
- Совместимость публичных и внутренних protobuf-контрактов проверяется автоматически.

## Проверяемые инварианты

- Браузер не может обратиться к внутреннему полному имени gRPC-метода.
- Внешняя ошибка не содержит служебных деталей.
- Отключение клиента отменяет связанный RPC или подписку.
- WS/SSE-клиент без прав не может подписаться на чужой канал.
- Роли пограничного слоя имеют независимые метрики готовности и нагрузки.

## Отложенные вопросы

- Выбор между Vue SPA и Nuxt.
- Формат восстановления пропущенных SSE-событий.
- Граница отдельного чата и политика хранения сообщений.
