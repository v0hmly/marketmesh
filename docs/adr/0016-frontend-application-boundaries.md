# ADR-0016: Границы приложений и возможностей frontend

- Статус: Принято в MM-87
- Дата: 2026-09-24
- Автор: v0hmly
- Уточняет: [ADR-0010](0010-microfrontend-composition-and-deployment.md)

## Решение

Storefront остаётся модульным Vue-приложением. Seller остаётся его модулем.
Staff — отдельное приложение и артефакт с собственным origin, SSO-сессией и
сетевым периметром. Runtime Module Federation не применяется. Версия платформы
остаётся общей; разделение сборок не вводит независимых релизов.

Владелец всех областей пока v0hmly. Разделение фиксирует ответственность кода,
не выдумывает существование отдельных команд.

```text
frontend/
  apps/storefront/src/
    shell/                 # запуск, маршруты, координация cookie-сессии
    modules/auth/          # вход, регистрация, email-ссылки, безопасность
    modules/account/       # каркас кабинета и возможности покупателя
      profile/ addresses/ settings/ avatar/ orders/ favorites/ reviews/
    modules/seller/        # заявка, вход, кабинет продавца
    shared/                # технические утилиты без доменных фасадов
  apps/staff/src/           # корпоративные SSO и приглашения, без buyer bootstrap
  packages/browser-client/ # общий транспорт HTTPS/Connect, без хранения токенов
  packages/design-system/  # используемые обоими приложениями примитивы и стили
  gen/                     # игнорируемая генерация публичных protobuf
```

## Сессия и данные

`SessionController` владеет Web Locks, журналом поколений, подтверждённым владельцем,
проверкой запоздалого ответа и состояниями неопределённого исхода. Он не знает
типов профиля, адресной книги и настроек, не содержит их операций и данных.
Account владеет этими операциями и применяет общий механизм проверки владельца.
Запись не повторяется автоматически. Подтверждённый отказ доступа при чтении
позволяет обновить сессию под exclusive lock и повторить только чтение.

Действующий серверный контракт идентичности — `UserService.GetMe`. Он проверяет
Auth assertion, а `PROFILE_NOT_READY` означает, что аутентификация уже состоялась,
но проекция User ещё не готова. На границе композиции адаптер передаёт в координатор
только `subject_id` либо состояние ожидания. Клиент не извлекает личность из Web
Storage, cookie или неподтверждённого JWT. Поля профиля не сохраняются в shell.
Так сохраняется последовательная совместимость существующих Auth/User; новый
Auth RPC для идентичности не требуется для этого изменения.

## Границы импортов

Модуль владеет своими API, контекстом внедрения, состоянием, валидацией, стилями и
тестами. Внешние потребители используют только явно объявленные публичные точки
входа: `auth/public.ts` (ошибки/валидация/типы) , `auth/ui.ts` (security UI)
и `auth/forms.ts` (оформление форм входа). Account и Seller могут зависеть
от этих интерфейсов Auth; обратной
зависимости нет. UI-export отделён, чтобы обычная ошибка не загружала security-экран.
Контексты Account/Seller принадлежат своим модулям. `shell/context` экспортирует
только сессию. Пакетам запрещены приложения и доменные protobuf.
Shell собирает приложения; shared не реэкспортирует домены и не предоставляет
Staff/Seller API. Тестовые составные фикстуры не входят в runtime-граф.

Проверяются обычные импорты, реэкспорты и динамические импорты. Нельзя обходить
границы через абсолютный путь, alias, соседнее приложение, общий контекст или
вычисляемый import. В браузер разрешены только публичные protobuf-контракты.

## Загрузка и оформление

Маршруты загружают представления по требованию штатными загрузчиками Vue Router.
Storefront не содержит staff; посещение покупательского маршрута не загружает
представления продавца. Ошибка загрузки чанка показывает действие обновления
страницы; автоматического цикла reload и повторения мутаций нет. HTML отдаётся
без долгого кеширования, хешированные ресурсы — неизменяемые.

Единственный источник значений палитры — `docs/design/design-system/tokens.json`.
Генератор создаёт CSS для документации и исполняемого пакета; оба результата
игнорируются Git. Существующие CSS-имена становятся алиасами токенов; визуальный
редизайн в MM-87 не входит. Общие примитивы реально используются обоими приложениями.

## Корпоративный контур

Для локального стенда владелец выбрал тестовый OIDC-провайдер.

| Граница | Реализация |
| --- | --- |
| Публичный origin | `https://localhost:18443`, только storefront и публичные buyer RPC |
| Staff origin | `https://staff.localhost:18444`, собственный артефакт/CSP и API |
| Локальный IdP | `https://oidc.localhost:18445`, только тестовые аккаунты |
| Callback | фиксированный `/sso/callback` на staff; state + browser binding + PKCE + nonce |
| Сеть | порты только `127.0.0.1`; отдельный bridge `staff-corporate`; обязательный корпоративный mTLS до HTTP |
| Хранилище | отдельная БД staff, RW/RO-роли в существующем PG primary/replica, verify-full |
| Cookie | `__Host-mm-staff-session`: Secure, HttpOnly, Strict, без Domain; login cookie Lax на 10 минут |
| Срок сессии | idle 30 минут, абсолютный 8 часов; проверяются сервером |

`staff-corporate` имеет gateway, нужный OrbStack для публикации loopback-портов;
`internal: true` отключал эту публикацию. OrbStack маршрутизирует опубликованные
порты между bridge и маскирует источник: один IP allowlist не является барьером.
Поэтому staff требует доверенный корпоративный **clientAuth-сертификат на TLS**
для каждого маршрута, включая статику, callback и RPC. Подсеть `172.31.87.0/24`
и loopback дополнительно проверяются по peer IP; forwarded-заголовки не учитываются.
`staff-storage` остаётся internal. Публичный gateway не содержит staff-маршрутов.

Локальный `browser.p12` — семидневный пропуск в этот контур, его один раз импортируют
в браузер с пустым паролем. PKI обновляется при истечении; после обновления пропуск
импортируют заново. Он не даёт роль сотрудника: дополнительно нужны OIDC и приглашение.
IdP не получает private client key, staff получает отдельную health identity;
публичные приложения не получают ни одну из них. Локальная модель не утверждает
наличие реального VPN. Корпоративная поставка сохраняет отдельный ingress/VPN/ACL
и выдачу mTLS от собственного CA. Feature flag защитой не является.

Staff service использует coreos/go-oidc для верификации токенов; браузер никогда
не получает OIDC-токены. Identity `(issuer, subject)` отделена от изменяемой почты.
Приглашения привязываются к verified email, потребляются транзакционно и не меняют
роль существующего участника. До приглашения доступны только собственная identity
и проверка приглашения. Чужие данные и бизнес-API отсутствуют.

Повторный вход отзывает старую сессию в same-origin StartSso: Strict cookie на
cross-site callback не приходит. Смена сессии сбрасывает staff-вкладки и исключает
применение запоздалых ответов. Подтверждённый вход возвращает на приглашение с
`#token`, новые ссылки не отправляют токен в HTTP URL.

Backend/протокол выкатываются до нового staff frontend: новые RPC и optional поле
StartSso добавлены совместимо. Старый публичный storefront после обновления не
обслуживает staff-маршруты. Возврат сотрудника идёт на отдельный origin; внешние
ссылки на прежний публичный `/staff` нужно заменить корпоративными, публичный
redirect с секретом приглашения не добавляется.

Команды, сертификаты и ограничения тестового IdP —
[руководство staff](../../frontend/apps/staff/README.md).

Бизнес-функции модерации и поддержки остаются в MM-59.

## Альтернативы и последствия

Оставить staff в storefront нельзя из-за общей сессии, графа загрузки и сетевого
периметра. Runtime Federation добавляет неподконтрольную композицию до появления
самостоятельных команд. Выносить Seller в ещё одно приложение пока нет основания:
он использует покупательский вход и общий цикл поставки. Поэтому две сборки и
направленные исходные зависимости дают требуемую изоляцию без runtime-протокола.
Цена решения — отдельные SSO/config/тесты и необходимость совместного обновления
общих пакетов. Общий PostgreSQL не добавляет ещё один инфраструктурный набор.

## Проверки и откат

Срезы проверяются отдельно: сессия и операции Account; отдельное приложение staff;
периметр/SSO; архитектурные отрицательные тесты; маршруты и артефакты; доступность
в обеих темах. Итоговая интеграционная проверка остаётся общей. Дополнительных
GitHub Actions jobs и платных возможностей GitHub это решение не требует.

Размеры и воспроизводимые команды — [бюджеты frontend](../frontend-bundles.md).

Frontend и конфигурация его обслуживающего контура откатываются согласованно.
Откат не открывает корпоративный API в публичной сети. Изменение структуры
frontend не требует переноса пользовательских данных. Staff добавляет собственную
БД/схему; обычный откат останавливает только staff и сохраняет её. Destructive down
не нужен для возврата frontend и требует отдельного решения о потере staff-данных.
