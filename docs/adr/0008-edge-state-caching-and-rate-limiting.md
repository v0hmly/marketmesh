# ADR-0008: Пограничное состояние, кэширование и ограничение частоты

- Статус: Принято
- Дата: 2026-08-31
- Авторы: команда проекта
- Заменяет: нет
- Заменено решением: нет

## Контекст

Пограничный слой должен защищать внутреннюю систему от всплесков и злоупотреблений, ограничивать запросы до дорогостоящей аутентификации и ускорять безопасные публичные чтения. Одновременно Redis в DMZ имеет другой профиль риска, чем хранилище сессий Auth.

Объединение этих состояний или кэширование ответов по умолчанию может раскрыть токены и персональные данные либо смешать ответы разных пользователей.

## Решение

Использовать два независимых экземпляра или кластера Redis:

- пограничный Redis в DMZ хранит счётчики, краткоживущий псевдонимный контекст сессии, безопасные публичные кэши и координацию realtime;
- внутренний Redis Auth хранит внешние сессии, MFA-состояние, ротацию обновления, отзыв и другие чувствительные данные аутентификации.

У них разные сетевые политики, роли, ключи шифрования, резервное копирование и сроки хранения. Прямого доступа DMZ к внутреннему Redis нет.

Ограничения применяются слоями:

1. глобальный предел и защита соединений;
2. предел по проверенному IP и подсети до аутентификации;
3. строгие отдельные пределы для входа, регистрации, восстановления и MFA;
4. предел по псевдонимному пользователю и сессии после проверки;
5. предел по публичному маршруту и его стоимости;
6. доменные бизнес-ограничения внутри сервиса.

Заголовкам Forwarded и X-Forwarded-* доверяют только при получении от известного балансировщика. В остальных случаях они удаляются. IPv6, прокси и NAT учитываются отдельной политикой, чтобы один адрес не был единственным сигналом.

Кэширование API запрещено по умолчанию. Разрешаются только явно перечисленные безопасные методы без побочных эффектов и персональных данных. Ключ кэша строится из нормализованного маршрута, версии контракта и явно разрешённых параметров. Ответы Auth и User по умолчанию имеют no-store.

SeaweedFS используется как объектное хранилище и origin, но не считается CDN. Доставка статических объектов через внешнюю CDN будет отдельным решением.

## Рассмотренные альтернативы

### Один Redis для DMZ и Auth

Дешевле и проще, но создаёт сетевой путь к чувствительному состоянию и общий радиус отказа.

### Только ограничения по IP

Работают до аутентификации, но неточны за NAT, обходятся распределёнными адресами и не ограничивают одного пользователя на разных устройствах.

### Только ограничения по пользователю

Не защищают дорогие точки входа до установления личности.

### Кэшировать все успешные GET/RPC-чтения

Увеличивает долю попаданий, но метод и статус не доказывают отсутствие персонализации или побочного эффекта.

### Локальные счётчики в каждом экземпляре

Не требуют Redis, но дают непредсказуемый общий лимит при горизонтальном масштабировании. Допустимы только как аварийный дополнительный слой.

## Последствия

### Положительные

- Компрометация пограничного Redis не раскрывает исходные сессии Auth.
- Защита работает до и после аутентификации.
- Кэшируемые данные имеют явную классификацию и владельца.
- Разные виды нагрузки получают независимые лимиты.

### Отрицательные и риски

- Два Redis увеличивают эксплуатационные расходы.
- Распределённые лимиты зависят от задержки и доступности пограничного Redis.
- Псевдонимный идентификатор всё ещё является чувствительным корреляционным данным.
- Ошибка нормализации ключа или инвалидации может раскрыть чужой ответ.

## Защитные и эксплуатационные требования

- В пограничном Redis запрещены внешний токен, внутреннее утверждение и профильные персональные данные.
- Ключи имеют пространство имён, версию и обязательный TTL.
- Скрипт или транзакция ограничения атомарны.
- Для Auth-точек при отказе Redis применяется закрытый или строго ограниченный аварийный режим.
- Для безопасного публичного чтения допустим локальный консервативный предел.
- Ответ сообщает клиенту только безопасную информацию о повторе, не внутреннюю ёмкость.
- Метрики не используют IP или идентификатор пользователя как высококардинальную метку.

## Проверяемые инварианты

- DMZ не может подключиться к внутреннему Redis Auth.
- Ключи и значения пограничного Redis проходят автоматическую проверку классификации.
- Поддельный X-Forwarded-For не меняет вычисленный адрес клиента.
- Метод без явной политики никогда не кэшируется.
- Ответ одного пользователя не извлекается по ключу другого.
- Недоступность Redis не снимает ограничения с входа и восстановления.

## Отложенные вопросы

- Конкретный алгоритм распределённого лимита и числовые значения.
- Политика IPv6-префиксов и доверенных прокси.
- Допустимость устаревшего публичного ответа при отказе внутренней зоны.
- Выбор внешней CDN.
