# ADR-0012: Структура монорепозитория и Go workspace

- Статус: Принято
- Дата: 2026-08-31
- Авторы: команда проекта
- Заменяет: нет
- Заменено решением: нет

## Контекст

MarketMesh объединяет независимо развёртываемые Go-сервисы, платформенные библиотеки, protobuf-контракты, Vue frontend и инфраструктуру. Репозиторий должен давать единый цикл разработки и проверки, но не позволять сервисам превращаться в набор пакетов с неявными прямыми зависимостями.

Единый корневой Go-модуль упрощает начальную настройку, однако не выражает границы развёртывания и позволяет случайно импортировать реализацию соседнего сервиса. Модуль на каждый пакет создаёт противоположную проблему: большое количество версий и служебных файлов без самостоятельной границы ответственности.

Нужна промежуточная гранулярность, при которой модуль совпадает с развёртываемым приложением или устойчивой общей областью кода, а команды проверки запускаются из корня репозитория.

## Решение

Использовать один Git-монорепозиторий и зарегистрированный в репозитории файл `go.work`. Отдельный Go-модуль создаётся для каждого развёртываемого сервиса, для платформенных библиотек в целом и для сгенерированных Go-контрактов.

Начальный набор модулей:

| Каталог | Путь модуля | Назначение |
| --- | --- | --- |
| `services/auth` | `github.com/v0hmly/marketmesh/services/auth` | Аутентификация и внешние сессии |
| `services/user` | `github.com/v0hmly/marketmesh/services/user` | Профиль и настройки пользователя |
| `services/gateway-in` | `github.com/v0hmly/marketmesh/services/gateway-in` | Публичная граница DMZ и сервер туннеля |
| `services/gateway-out` | `github.com/v0hmly/marketmesh/services/gateway-out` | Внутренний ретранслятор исходящего туннеля |
| `platform` | `github.com/v0hmly/marketmesh/platform` | Общие технические библиотеки, включая logger и telemetry |
| `api/gen/go` | `github.com/v0hmly/marketmesh/api/gen/go` | Только сгенерированный Go-код контрактов |

`go.work` разрешает локальные зависимости без директив `replace` в `go.mod`. Директива `replace` на локальный путь в регистрируемом `go.mod` запрещена. Каждый модуль обязан собираться и тестироваться как в workspace, так и с `GOWORK=off` после появления межмодульных зависимостей и зафиксированных версий.

На текущем этапе модули версионируются и выпускаются вместе с платформой MarketMesh. Сам факт отдельного `go.mod` не означает независимый релиз. Изменение стратегии версионирования принимается отдельным ADR.

### Каталоги монорепозитория

```text
marketmesh/
├── api/
│   ├── proto/
│   └── gen/
│       ├── go/
│       └── ts/
├── frontend/
│   ├── apps/
│   └── packages/
├── infra/
│   ├── compose/
│   └── kubernetes/
├── platform/
├── services/
│   ├── auth/
│   ├── user/
│   ├── gateway-in/
│   └── gateway-out/
├── tools/
├── docs/
├── go.work
├── pnpm-workspace.yaml
└── Taskfile.yml
```

`api/proto` является источником публичных, внутренних и туннельных protobuf-схем. `api/gen/go` и `api/gen/ts` содержат только воспроизводимо сгенерированные результаты и не редактируются вручную.

`frontend` является pnpm workspace. До выполнения критериев ADR-0010 используется одно модульное Vue-приложение, а не runtime-композиция микрофронтендов. Общий frontend-пакет создаётся только для кода, который действительно используют несколько продуктовых модулей.

`infra` содержит локальный Docker Compose и Kubernetes-манифесты. Окружения, секреты и правила сетевой изоляции не смешиваются с кодом приложения.

`tools` содержит только автоматизацию репозитория. Инструмент, который становится самостоятельным продуктом или развёртываемым процессом, получает собственный модуль и явно добавляется в workspace.

### Правила зависимостей

Допустимый граф верхнего уровня:

```text
services/* -> platform
services/* -> api/gen/go
frontend/* -> api/gen/ts
```

- сервис не импортирует модуль другого сервиса;
- `platform` не зависит от сервисов и сгенерированных контрактов;
- `api/gen/go` и `api/gen/ts` не зависят от сервисов или `platform`;
- платформенная библиотека не становится местом для общей бизнес-модели;
- межсервисное взаимодействие выполняется только через контракт или событие;
- внутренние пакеты каждого Go-модуля дополнительно защищены механизмом `internal`;
- зависимость между пакетами `platform` должна оставаться направленным ациклическим графом и обосновываться реальным повторным использованием.

Корневые команды Task и совместимые команды Make перебирают все Go-модули из утверждённого списка и выполняют форматирование, сборку, vet и тесты. Оба интерфейса вызывают единый workspace-скрипт и не дублируют логику обхода модулей. Отдельная проверка сверяет пути модулей и запрещённые межмодульные импорты. Добавление или удаление модуля должно атомарно обновлять `go.work`, проверяющий инструмент и этот ADR либо заменяющее его решение.

Docker-образ сервиса собирается с контекстом корня монорепозитория, чтобы сборка могла получить сгенерированные контракты и платформенные модули. Dockerfile при этом находится рядом с сервисом или в согласованном каталоге поставки и копирует только необходимые файлы.

## Рассмотренные альтернативы

### Один Go-модуль в корне

Даёт самые простые команды и обновление зависимостей, но ослабляет границы сервисов и позволяет прямые импорты между ними. Для учебного проекта также скрывает важную часть эксплуатации независимых микросервисов.

### Отдельный модуль для каждой платформенной библиотеки

Максимально изолирует logger, telemetry и будущие библиотеки, но преждевременно создаёт много циклов версионирования. Пакеты внутри одного модуля `platform` уже имеют отдельные API и могут быть выделены позднее.

### Один backend-модуль и отдельный frontend workspace

Проще полного multimodule-подхода, но не даёт модульной границы каждому развёртываемому сервису.

### Отдельный репозиторий на сервис

Обеспечивает сильную организационную изоляцию, но усложняет атомарное изменение контрактов, локальную разработку и обучение. Такое разделение оправдано при независимых командах и циклах поставки, которых сейчас нет.

## Последствия

### Положительные

- Граница Go-модуля совпадает с единицей развёртывания или общей технической областью.
- Все части проекта разрабатываются и проверяются из одного checkout.
- Случайная зависимость одного сервиса от другого выявляется автоматически.
- Локальное изменение контракта или platform-пакета сразу доступно сервисам через `go.work`.
- Структура допускает последующее выделение модуля или репозитория без переписывания внутренней архитектуры сервиса.

### Отрицательные и риски

- Несколько `go.mod` требуют синхронного обновления зависимостей и отдельных файлов `go.sum`.
- Простая команда `go test ./...` из корня не охватывает все вложенные модули, поэтому обязательна корневая автоматизация.
- Workspace может скрыть отсутствие опубликованной версии локального модуля; это проверяется отдельно с `GOWORK=off` перед выпуском.
- Docker build context из корня требует аккуратного `.dockerignore` и контроля копируемых файлов.

## Защитные и эксплуатационные требования

- Корневые проверки не загружают и не исполняют код из непроверенных сгенерированных каталогов вне стандартного процесса генерации.
- Файлы с секретами, локальные `.env`, ключи и артефакты сборки исключены из Git и Docker context.
- Код сервиса не получает доступ к данным другого сервиса через общую библиотеку или прямой драйвер БД.
- Сгенерированные файлы воспроизводимы из зафиксированных схем и версий инструментов.
- Изменение общих модулей запускает проверки всех их потребителей.

## Проверяемые инварианты

- Все пути `module` начинаются с `github.com/v0hmly/marketmesh/` и соответствуют каталогу.
- `go.work` содержит каждый утверждённый Go-модуль ровно один раз.
- `task build`, `task test` и `task verify`, а также их Make-эквиваленты выполняются из корня репозитория.
- Граф импортов не содержит зависимости `services/<a>` от `services/<b>`.
- `platform` не импортирует сервисы или сгенерированные контракты.
- Сгенерированные контракты не импортируют `platform` или сервисы.
- В `go.mod` нет зарегистрированных `replace` на локальный путь.
- В Git отсутствуют каталоги зависимостей, секреты и результаты локальной сборки.

## Отложенные вопросы

- Выделение отдельных модулей из `platform` после появления независимого версионирования.
- Точная политика обновления общих зависимостей и автоматизация change detection в CI.
- Версионирование и публикация сгенерированных контрактов вне монорепозитория.
- Инструменты сборки контейнеров и стратегия кэширования multimodule-контекста.
