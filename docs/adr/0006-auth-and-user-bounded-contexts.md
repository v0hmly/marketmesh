# ADR-0006: Границы сервисов аутентификации и пользователей

- Статус: Принято
- Дата: 2026-08-31
- Авторы: команда проекта
- Заменяет: нет
- Заменено решением: нет

## Контекст

На первом этапе нужны сервис аутентификации и сервис пользователей. Если оба сервиса читают общие таблицы или синхронно вызывают друг друга в обе стороны, независимое развитие и отказоустойчивость будут только формальными.

Учётные данные имеют более высокий уровень чувствительности, чем большая часть профиля. Их совместное хранение расширяет доступ сервиса пользователей и увеличивает последствия его компрометации.

## Решение

Разделить ответственность следующим образом.

Сервис аутентификации владеет:

- учётными записями и неизменяемым идентификатором субъекта;
- парольными хэшами, MFA, WebAuthn и восстановлением;
- внешними сессиями, обновлением и отзывом;
- ключами подписи и обменом сессии на внутреннее утверждение;
- событиями безопасности и блокировкой входа.

Сервис пользователей владеет:

- отображаемым профилем и настройками;
- адресами и контактными данными, не являющимися учётными данными входа;
- метаданными аватара;
- пользовательскими предпочтениями и будущими профильными атрибутами.

У каждого сервиса отдельная база или логически и операционно изолированная БД PostgreSQL, отдельная роль и миграции. Между базами нет внешних ключей и прямых SQL-запросов. Общим ключом является непрозрачный неизменяемый идентификатор субъекта.

Регистрация выполняется без распределённой транзакции:

1. Auth сохраняет учётную запись и запись outbox одной локальной транзакцией.
2. Событие регистрации публикуется в NATS JetStream.
3. User идемпотентно создаёт профиль.
4. Состояние «учётная запись создана, профиль ещё создаётся» является допустимым и наблюдаемым.

Между Auth и User запрещён синхронный цикл. Если одному сервису нужны данные другого, применяется явно направленный API или локальная проекция из событий. Auth не включает профильные данные во внутреннее утверждение.

## Рассмотренные альтернативы

### Один сервис Identity

Проще начать и обеспечивает локальную транзакцию, но смешивает особо чувствительные учётные данные с быстро растущим профилем.

### Два сервиса с общей базой

Ускоряет запросы и согласование схемы, но не даёт реального владения данными и позволяет обходить API.

### Синхронное создание профиля из Auth

Даёт немедленную согласованность, но делает регистрацию зависимой от доступности User и подталкивает к компенсациям между базами.

### Распределённая транзакция

Скрывает промежуточное состояние, но усложняет инфраструктуру, связывает сервисы и плохо сочетается с автономным владением данными.

## Последствия

### Положительные

- Доступ к учётным данным ограничен минимальным числом компонентов.
- Сервисы могут независимо менять схему и масштабироваться.
- Отказ User не блокирует безопасное сохранение новой учётной записи.
- Границы соответствуют разным моделям угроз и срокам хранения.

### Отрицательные и риски

- Появляется временная согласованность между регистрацией и профилем.
- Потребуются сценарии повторной обработки, сверки и удаления данных.
- Запрос, которому нужны обе категории данных, не может использовать SQL JOIN.
- Ошибочная классификация контактного поля может создать дублирование владельцев.

## Защитные и эксплуатационные требования

- Роли БД не имеют прав на базу другого сервиса.
- Auth не публикует парольные хэши, MFA-секреты и внешние сессии в событиях.
- События содержат минимум персональных данных.
- Действия с учётными данными имеют отдельный аудит.
- Профиль создаётся идемпотентно по идентификатору субъекта.
- Для удаления и обезличивания будет определён координируемый процесс с локальными подтверждениями.

## Проверяемые инварианты

- User не может подключиться к БД Auth, а Auth — к БД User.
- Повтор события регистрации не создаёт второй профиль.
- Внутреннее утверждение не содержит имя, email или адрес.
- Временная недоступность NATS не откатывает сохранённую учётную запись и outbox.
- В графе обязательных синхронных вызовов нет цикла Auth ↔ User.

## Отложенные вопросы

- Какой сервис владеет подтверждённым email, если он одновременно используется для входа и связи.
- Процесс полного удаления пользователя и сроки хранения аудита.
- Сценарий объединения и разделения учётных записей.
