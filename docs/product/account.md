# Аккаунт и личный кабинет покупателя

Модель подтверждена пользователем 17 сентября 2026 года: профиль — имя и «о себе»;
адресная книга — несколько адресов с получателем, телефоном, страной, индексом,
городом, улицей/домом, квартирой и комментарием; настройки — тема оформления.
Один адрес не заменяет всю книгу. Ниже зафиксированы правила первого среза и
технические ограничения. Текущее состояние реализации и дальнейшие задачи —
в [аудите кабинета](account-remaining.md).

## Реализованные поля и границы владения

[Auth](../../api/proto/auth/v1/auth.proto) владеет идентификатором входа,
паролем и сессиями. [User](../../api/proto/user/v1/user.proto) владеет профилем,
адресной книгой, настройками и метаданными аватара. Общий ключ — неизменяемый
непрозрачный subject ID. Изменение профиля или адресного контакта не меняет
учётные данные Auth; границы заданы [ADR-0006](../adr/0006-auth-and-user-bounded-contexts.md).

| Поле | Текущий серверный контракт |
| --- | --- |
| `identifier` | Нормализованная ASCII-почта, 3–254 байта. Перед первым входом подтверждается ссылкой; display name, комментарии и SMTPUTF8 не принимаются. |
| `password` | Новые пароли: 8–64 Unicode-символа, до 72 байт UTF-8, без U+0000; строчная/заглавная латинские буквы, цифра и спецсимвол, который не является буквой, цифрой, пробелом или управляющим символом. Старые пароли проверяются без навязывания новых требований. |
| `display_name` | Необязательное имя; не более 320 байт исходного UTF-8, после trim не более 80 Unicode-символов; управляющие символы запрещены. |
| `bio` | Необязательный обычный текст, не HTML; до 1000 Unicode-символов и 4000 байт; из управляющих символов разрешены перенос строки и табуляция. |

Проверки соответствуют доменам [credential](../../services/auth/internal/domain/credential/credential.go)
и [profile](../../services/user/internal/domain/profile/profile.go). Клиентские
ограничения должны учитывать разницу между байтами UTF-8 и символами, а сервер
остаётся источником окончательной валидации.

`GetMe` не принимает идентификатор владельца. `UpdateMe` заменяет оба редактируемых
поля и требует последнюю прочитанную `expected_version`; успешный ответ содержит
сохранённый профиль с новой версией. Subject ID, версия и время создания/изменения
не редактируются пользователем. Новые персональные поля в профиль не добавляются
автоматически.

## Регистрация, вход и состояния интерфейса

Формы используют почту и пароль. MM-90 подключает настоящий backend и локальный
Mailpit: после регистрации нужно подтвердить почту, затем войти. Подтверждение
входа кодом покупатель включает сам в `/account/security`. При включённом коде
cookie выдаются только после его проверки; иначе — сразу после пароля.
Сроки, защита от перебора и уведомления описаны в [Auth email](../security/auth-email.md).

Создание профиля после регистрации асинхронно: Auth outbox → JetStream → User
inbox. Отсутствующий пока профиль не означает отсутствие действующей сессии.

| Состояние | Поведение кабинета |
| --- | --- |
| Загрузка | Понятный индикатор; повторная отправка формы заблокирована до результата. |
| `NotFound` с `ErrorInfo` домена `marketmesh.user`, причиной `PROFILE_NOT_READY` | «Профиль создаётся», повторное чтение с ограниченной частотой и ручной повтор; сессия сохраняется. Другой `NotFound` не считается этим состоянием. |
| `InvalidArgument` | Исправление введённых значений; серверная ошибка не заменяется сообщением об успешном сохранении. |
| `Aborted` при сохранении профиля | Конфликт версии: сохранить черновик, предложить прочитать актуальные данные и согласовать изменения; не перезаписывать их автоматически. |
| `Unauthenticated` | Shell выполняет согласованный сценарий обновления сессии либо переводит к входу. |
| `PermissionDenied` | Показать отказ доступа; обновление сессии не используется для обхода запрета. |
| Потеря сети, timeout, временная недоступность | Показать возможность повторить действие; для записи исход может быть неизвестен, сначала прочитать актуальное состояние. |
| Успешное сохранение | Показать подтверждение и использовать профиль из ответа; данные доступны после перезагрузки и повторного входа. |

Форма «О себе» сохраняет несохранённый черновик при ошибке и предупреждает о его
потере при уходе со страницы. Обязательны доступные подписи полей, сообщения об
ошибках и управление с клавиатуры.

## Сессия и ответственность storefront

По [ADR-0010](../adr/0010-microfrontend-composition-and-deployment.md) используется
модульное [Vue-приложение storefront](../../frontend/apps/storefront/README.md).
Shell владеет запуском, верхней маршрутизацией, состоянием сессии, применением
темы и общими ошибками. Модуль аккаунта владеет профилем, адресами, формами и их
доменным состоянием. Общий глобальный store не хранит доменные данные; общие
пакеты содержат только действительно переиспользуемые примитивы.

Браузер использует сгенерированные публичные Auth/User-контракты через шлюзы;
внутренние assertion API и `gateway.v1.UserBrowserService` ему не доступны.
Транспорт описан в [протоколе туннеля](../architecture/tunnel-protocol.md).
Внешние токены находятся только в Secure/HttpOnly cookie, не выдаются JavaScript
и не сохраняются в Web Storage. Персональные ответы имеют `Cache-Control: no-store`.

Lifecycle интерфейса:

1. После загрузки защищённого раздела прочитать `GetMe`.
2. При `Unauthenticated` выполнить один координированный `RefreshSession`, затем
   повторить чтение. Координация нужна и между параллельными запросами, и между
   вкладками: повтор использованного refresh отзывает семью сессии.
3. Не повторять автоматически запись `UpdateMe` или неоднозначно завершившийся
   refresh. После сетевой ошибки не объявлять пользователя разлогиненным только
   по факту недоступности сети.
4. При подтверждённом истечении/отзыве сессии очистить персональное состояние и
   закрыть защищённые разделы. При `Logout`/`LogoutAll` скрыть локальные данные;
   успешный серверный отзыв подтверждать только после ответа, ошибку сети показывать
   отдельно. При следующем входе загрузить профиль заново.

Координатор сессии обязан сериализовать смену аккаунта, refresh и выход между
вкладками. Перед отправкой изменения сессии он сохраняет признак незавершённой
операции без токенов и персональных данных: после закрытия вкладки или неизвестного
сетевого результата автоматический повтор refresh запрещён. Если браузер не
обеспечивает надёжную координацию и сохранение этого признака, автоматический
refresh ограничивается явно, а не заменяется ненадёжной блокировкой.

Запись из формы привязана к аккаунту и поколению сессии, в котором она открыта:
форма покупателя A не должна отправиться с cookie покупателя B после входа в
другой вкладке. При смене поколения очищаются персональные данные; запоздалые
ответы предыдущего поколения не восстанавливают их. Выход с истёкшим access
требует ограниченного безопасного восстановления по тем же правилам координации;
отказ Auth или неизвестный результат не считаются успешным отзывом.

Список устройств, новый session lifecycle и инфраструктура уведомлений сюда не
добавляются. Действующие свойства cookie и проверки Origin описаны в
[документации Auth](../../services/auth/README.md).

## Адресная книга

Покупатель хранит до 20 адресов. У каждой записи серверный непрозрачный
`address_id`; владелец определяется проверенной сессией. При создании, изменении,
удалении и выборе основного адреса клиент передаёт последнюю прочитанную версию
книги. Изменение одной записи не заменяет остальные записи. У профиля, книги и
настроек независимые версии: сохранение имени не конфликтует с адресом или темой.

| Поле | Правила первого среза |
| --- | --- |
| Получатель | Обязательно, до 120 Unicode-символов. |
| Телефон получателя | Обязательно, до 32 символов; 7–15 цифр, разрешены пробелы, `+`, `-`, `.`, `(`, `)`. Формат сохраняется после trim; номер не считается подтверждённым и не меняет логин. |
| Страна | Обязательно, обычное название до 80 Unicode-символов. Кабинет не ограничивает географию доставки; правила оформления определит MM-55. |
| Почтовый индекс | Необязательно, до 20 Unicode-символов. |
| Город / населённый пункт | Обязательно, до 120 Unicode-символов. |
| Улица и дом | Обязательно, до 240 Unicode-символов одним полем. |
| Квартира / помещение | Необязательно, до 40 Unicode-символов. |
| Комментарий | Необязательный обычный текст, до 500 Unicode-символов; не HTML. |

Строки должны быть UTF-8; крайние пробелы удаляются, управляющие символы запрещены,
кроме переноса строки и табуляции в комментарии. Для каждого поля есть также
предел исходных UTF-8 байтов: четыре байта на разрешённый Unicode-символ, для
ASCII-телефона — 32 байта. Сервер остаётся источником окончательной валидации.

Первый адрес в пустой книге становится основным. В непустой книге основным
становится только явно выбранный адрес. Основной адрес может быть только один.
Удаление основного не удаляет другие записи и не назначает новый автоматически:
покупатель выбирает его явно. Повторное добавление в пустую книгу снова назначает
первый адрес основным. Удаление всегда требует подтверждения в интерфейсе.

Операции возвращают актуальный снимок книги с владельцем и новой версией. Конфликт
версий сохраняет черновик и требует явного согласования. Неоднозначно завершившееся
создание не повторяется автоматически: сначала перечитывается книга, затем
пользователь решает, требуется ли ещё одна запись. Чужой и отсутствующий ID
возвращают одинаковое безопасное состояние отсутствия адреса.

MM-55 будет выбирать адрес через согласованную границу и сохранять данные получения
на момент покупки; изменение адресной книги не должно менять оформленный заказ.
Адреса не передаются в browser storage, URL, telemetry или общие кэши.

## Настройки

Поддерживается `theme = system | light | dark`, по умолчанию — `system`. User
хранит предпочтение текущего владельца и отдельную версию настроек; shell применяет
подтверждённую сервером тему. Настройка восстанавливается после входа и перезагрузки.
При выходе или смене владельца применяется системная тема, а запоздалый ответ
старого владельца игнорируется. Изменение темы не затрагивает профиль или адреса.
Произвольное хранилище настроек и переключатели несуществующих уведомлений не
создаются; уведомления относятся к MM-58.

## Безопасность аккаунта и следующие задачи

MM-90 реализует почтовые хендлеры, typed browser-обёртки шлюзов, SMTP outbox,
восстановление и смену пароля/email, настройку кода и свои сеансы.
Резервные коды выделены в MM-91, удаление аккаунта с реальным исполнением
30-дневного срока и очисткой данных — в MM-92. Эти действия не объявляются
успешными через ещё не реализованные contract-first RPC.

Кабинет покупателя по прототипам включает заказы, избранное, отзывы и раздел
MarketMesh ID (личные и публичные данные, сеансы, удаление аккаунта); поля
профиля MM-81 добавлены в [user.proto](../../api/proto/user/v1/user.proto)
аддитивно. Совмещённый email для входа и связи остаётся владением Auth по
ADR-0006 и не дублируется в User. Social login автоматически не добавляется.

Аватар перенесён из шага 17 MM-50 в отдельную задачу MM-65 после MM-43: только проверенный файл
владельца и безопасная производная, без самостоятельного upload в кабинете.
«Мои покупки» перенесены из шага 18 в MM-66 после реального API MM-55: собственные
заказы и детали; состав, суммы, статусы и действия определяет домен заказов.
Mock-данные не считаются готовностью этих функций. По решению пользователя от
17 сентября 2026 года текущая поставка MM-50 сначала доводит сам кабинет;
интеграции аватара и покупок с зависимостями MM-43/MM-55 переносятся в итоговый
список дальнейших задач и не блокируют эту поставку.
