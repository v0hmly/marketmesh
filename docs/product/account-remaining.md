## Результат текущей поставки

1. **Состав полей согласован — MM-50, шаг 01.** Правила, обязательность и ограничения первого среза зафиксированы в [модели](account.md). Адресная книга содержит несколько записей; это не единственный адрес пользователя.
2. **Текстовый профиль реализован — MM-63, шаги 09–12.** Согласованные имя/«о себе» соответствуют действующим GetMe/UpdateMe и UI. PR69 слит и проверен; Это объём первого среза; серверное хранение дополнительных полей экрана MM-85 подключается в MM-93.
3. **MM-68: адресная книга реализована — шаги 07/13.** До 20 адресов с восемью полями, создание/чтение/редактирование/удаление и основной адрес, owner-only доступ, отдельная версия книги и серверная валидация. UI сохраняет черновик при конфликте и требует явного решения после неоднозначной записи. Реальный E2E проверяет повторный вход, чужие ID, потерянный ответ на выполненную запись и максимальную Unicode-книгу более 64 KiB. Выбор адреса и неизменяемые данные получения в заказе должны затем согласовываться с MM-55.
4. **MM-69: тема оформления реализована — шаги 08/14.** User хранит system/light/dark с отдельной версией; shell применяет подтверждённое значение после входа и перезагрузки, сбрасывает к системному при выходе или смене владельца. Конфликты сохраняют выбор, потерянный ответ требует перечитывания без автоматического повтора записи. Проверены светлая/тёмная палитры и системное переключение.
5. **Сквозная проверка выполнена — шаг 16.** Реальный MM-64 E2E после [PR72](https://github.com/v0hmly/marketmesh/pull/72) подтверждает регистрацию Auth→outbox→JetStream→User, профиль, несколько адресов и тему. Проверены повторный вход, изоляция владельцев, конфликт двух вкладок, независимость трёх версий, потерянные ответы на выполненные записи, максимальная книга и отзыв сессий. Chromium и Node проверяют доверенный TLS; подмены сервисов и SQL-заготовок профиля в этом прогоне нет.
6. **Срезы и эпик приняты.** MM-63/MM-64/MM-68/MM-69 слиты в epic ([PR69](https://github.com/v0hmly/marketmesh/pull/69), [PR70](https://github.com/v0hmly/marketmesh/pull/70), [PR72](https://github.com/v0hmly/marketmesh/pull/72), [PR73](https://github.com/v0hmly/marketmesh/pull/73), [PR74](https://github.com/v0hmly/marketmesh/pull/74)) и переведены в done после полного E2E и обязательных проверок. Шаги 01–16 приняты. После слияния эпика в dev через [PR76](https://github.com/v0hmly/marketmesh/pull/76) MM-50 переведён в done. ## Решения и эксплуатационная готовность

- **MM-70: доступность при перераспределении обратных туннелей — todo.** Расширенный E2E выявил 503 в момент периодического закрытия рабочего туннеля. Локальный контур MM-64 использует фиксированную пару и отключает периодическое перераспределение только в `ENVIRONMENT=test`. Для production нужно обеспечить покрытие экземпляров Gateway In при rolling/maxSurge и отказах, устанавливать замену до закрытия рабочего пути и не перераспределять последний оставшийся путь. Повторять мутации автоматически нельзя; локальный режим не закрывает эту задачу.

- **MM-90: почта и безопасность Auth.** Реальные подтверждение адреса, опциональный код, смена/сброс пароля, смена почты, свои сеансы и уведомления через локальный Mailpit. Детали — [Auth email](../security/auth-email.md). Следующие части поручения: MM-91 резервные коды, MM-92 удаление аккаунта с очисткой данных, MM-93 серверная модель личных данных. Social login и корпоративный SSO не входят в этот срез.
- **MM-67: обновить базовые контейнеры и повторить сканирование — todo.** В использованных PostgreSQL/Redis images обнаружены соответственно 118/8 HIGH или CRITICAL, 25/8 имеют опубликованное исправление. В отдельном Chromium test image после доступных обновлений остались 79 HIGH и 7 CRITICAL ОС без доступных исправлений. Runtime-образ приложений после закреплённого обновления OpenSSL и NATS имеют 0 HIGH/CRITICAL. Нужны проверенные обновления общей базы образов, повторные интеграционные проверки и учёт остаточных находок перед эксплуатационной поставкой; локальный тестовый контур не означает production readiness.
- **MM-6: CI и проверки безопасности.** Существующая задача остаётся todo до отдельного подтверждения пользователя. Нужны автоматические Go/frontend/API/security проверки и required checks. Пока применяется записанное в проекте исключение с локальными проверками и независимым review; отсутствие GitHub CI не называется успешным CI.
- **Эксплуатационная конфигурация.** MM-64 рассчитан на локальную изолированную сеть и loopback, использует временный CA, plaintext PostgreSQL/Redis внутри сети и часть root-контейнеров. Для внешней поставки нужны конфигурация окружения, управляемая ротация сертификатов/ключей и проверка ограничений контейнеров по общим задачам платформы.

Проверенные ограничения браузера: Web Locks и доступное хранилище журнала обязательны для безопасной координации сессии. При отсутствии поддержки интерфейс объясняет ограничение. Расширение совместимости требует отдельного продуктового решения.

Основания: [модель кабинета](account.md), публичные контракты [Auth](../../api/proto/auth/v1/auth.proto) и [User](../../api/proto/user/v1/user.proto), storefront, проверенные изменения MM-64, задачи MM-50/43/55/6 и независимый аудит. Реальный MM-64 прогон pending/core — passed, 0 failed; 84 frontend unit/component tests и 8 Chromium-проверок с axe, TypeScript/lint/build, Go workspace/race/vet/protobuf и standalone module проверки пройдены; Gitleaks изменённых исходников — 0 находок.
