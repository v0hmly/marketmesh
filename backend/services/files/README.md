# Files: приватная загрузка и безопасная выдача

MM-43; архитектура и границы доверия — [ADR-0015](../../../docs/adr/0015-private-file-data-plane.md).
Приёмка текущего dev и оставшиеся CVE описаны в
[решении владельца](../../../docs/security/files-dev-acceptance.md).
Обязательное выключение Files не является условием слияния. Флаги остаются
параметрами подключения к настроенным Auth, mTLS, S3/KMS и БД.
[Полный локальный DC E2E](../../../docs/testing/files-dc-e2e.md) проверяет отказ
обоих логических DC на OrbStack. CVE отслеживаются в MM-88/MM-67, будущие
физические fault domains — в MM-89.

## Поведение

- До 100 МиБ: JPEG, PNG, PDF, DOCX, XLSX, PPTX, ODT, ODS, ODP.
- Макросы, шифрование, вложенные архивы/объекты, внешние связи и бинарные
  DOC/XLS/PPT запрещены. MIME и структура проверяются независимо от расширения.
- Изображение выдаётся как новый PNG без EXIF; PDF и офисный документ — как
  новый PDF из изображений страниц. Редактируемость, текстовый слой,
  цифровые подписи, ссылки, формы и вложения не сохраняются.
- Клиент заранее вычисляет SHA-256 всего файла и каждой части по 5 МиБ.
  `CreateUpload` с неизменным idempotency key/manifest возобновляет загрузку;
  ответ содержит принятые части и новые PUT capabilities только для отсутствующих.
- URL действует не более 60 секунд и связывает метод, key, точный размер,
  checksum, SSE-KMS и `If-None-Match: *`. Клиент отправляет указанные заголовки;
  браузер самостоятельно выставляет запрещённые для ручного задания `Host` и
  `Content-Length`. Повторный PUT принятой части возвращает 412: нужно запросить
  состояние сессии, а не перезаписывать часть.
- `CompleteUpload` фиксирует manifest в БД, затем обработка асинхронна.
  `CreateDownload` доступен только владельцу в READY и выдаёт attachment/no-store.
  Клиент проверяет размер и `clean_sha256` до сохранения/открытия результата.
  Download URL — bearer capability; не сохранять его в аналитике, логах и истории.
- `Delete` подтверждает tombstone. Worker отдельно удаляет все копии и
  повторяет очистку при отказах. Уже выданный URL может работать до expiry
  (до 60 секунд); успешный Delete не обещает немедленное физическое стирание.

Личный tenant равен подтверждённому Auth subject. Общий доступ и
межорганизационные ACL в этой версии не предусмотрены.

## Процессы и конфигурация

`cmd/files` запускается с `FILES_CONFIG_FILE=/absolute/private/config.json`.
Файл: обычный, до 64 КиБ, права 0600; неизвестные JSON-поля запрещены.
`Role` равен `control` либо `worker`. Секреты не передаются аргументами CLI.
[Локальный bootstrap](../../../infra/files-local/local.py) создаёт конкретные
`control.json` и `worker.json` без секретов в git или stdout.

Общие поля: `DatabaseRW`, `DatabaseRO`, `StorageCA`, `Quarantine`, `Delivery`.
Два delivery endpoint должны отличаться. Каждый bucket содержит `APIEndpoint`,
`PublicEndpoint`, `Bucket`, `KMSKey`, `Control {AccessKey, SecretKey}`;
control-роль дополнительно имеет отдельный `Capability {AccessKey, SecretKey}`.
В worker capability credentials запрещены; в control нет ключей внутреннего clean.

БД использует разные RW/RO роли и `sslmode=verify-full`. RW DSN явно содержит
`synchronous_commit=remote_apply`; сервер обязан иметь synchronous standby.
Изменения состояния и чтение для авторизации идут в RW, чтобы не читать
устаревшее состояние. RO нужен для replica/readiness и проверок сохранности.
Миграции в `migrations/` применяет отдельная bootstrap/migration роль.
Runtime не создаёт роли, схемы, buckets или KMS keys.

Worker: `Internal` bucket, `TempDir`, `ClamSocket`, `SandboxSocket`.
Одна итерация обрабатывает один durable job, deadline 8 минут, lease 10 минут.
Предыдущий worker после takeover не может опубликовать READY благодаря CAS.
Повторная обработка пишет кандидата по SHA-256; победивший manifest определяет
единственную выдаваемую производную. Все зависимости закрываются при ошибке.

Control: `Control.Enabled=true` включает только приватный scoped mTLS listener.
Нужны `Address`, `TLS {Certificate,PrivateKey,RootCA}`, `Own` и `Gateway` —
объекты `{TrustDomain,Environment,Cluster,Namespace,ServiceAccount}`.
`AuthTLS` имеет тот же формат TLS-файлов; `AuthTarget`, `AuthServerName`, `AuthURI`
и `Issuer` задают частный Auth endpoint и полный ожидаемый scope.
Сертификаты действуют не более 24 часов; URI имеет вид:

```text
spiffe://marketmesh.example/env/dev/cluster/dc-a/ns/marketmesh/sa/files
```

Опциональный `/pod/<uuid>` записывается в аудит и не расширяет права.
Auth заново проверяется на каждой операции: подпись/issuer/audience/scopes,
срок assertion и актуальное состояние сессии. JWT не кэшируется как разрешение.

## Подключение в dev

1. Auth: `AUTH_SESSION_AUDIENCES` включает `"files":["files:read","files:write"]`.
   Отдельный `AUTH_FILES_SCOPED_ENABLED=true` listener требует
   `AUTH_FILES_ADDRESS`, `AUTH_FILES_TLS_CERT_FILE`, `AUTH_FILES_TLS_KEY_FILE`,
   `AUTH_FILES_CLIENT_CA_FILE`, `AUTH_FILES_OWN_URI` (sa/auth) и
   `AUTH_FILES_EXPECTED_URI` (sa/files). Legacy Files URI там не работает.
2. Запустить приватный Files control и worker с отдельными IAM/DB roles.
3. Gateway-out: `FILES_BROWSER_ENABLED=true`, `FILES_TARGET`,
   `FILES_SERVER_NAME`, `EXPECTED_FILES_URI`, `FILES_TLS_CERT_FILE`,
   `FILES_TLS_KEY_FILE`, `FILES_TLS_ROOT_CA_FILE`. Проверить имена переменных по
   [конфигурации gateway-out](../gateway-out/internal/app/config.go).
   Сертификат gateway-out содержит полный scope; его кластер и namespace
   должны совпадать с ожидаемыми на Files. При недоступном Files readiness падает.
4. Gateway-in: `FILES_BROWSER_ENABLED=true`. Только пять фиксированных Connect
   методов `files.v1.FileService`; TLS, POST, запрос 16 КиБ, ответ 64 КиБ.
   Публичный body не задаёт browser context: gateway-in собирает его из HTTP.
   Gateway-out заменяет внешние credentials внутренним assertion audience files.

Крупные байты идут напрямую в object storage. Этот флаг не добавляет UI загрузки
и не позволяет передавать байты через туннель.

## Лимиты и эксплуатация

Лимиты на владельца: 10 активных uploads и 100 новых за последние 24 часа.
Идемпотентные повторы не расходуют квоту. Upload истекает через 24 часа;
обработка — через 48 часов от создания. Quarantine lifecycle — 3 дня;
worker раньше удаляет исходники READY и ненужные clean-кандидаты.
Tombstones сохраняются, очистка повторяется каждый час. Claim сначала выбирает
SCANNING/REPLICATING, затем просроченные UPLOADING и только потом READY/tombstone
для очистки; внутри группы — старейший `updated_at`, затем `id`. Активные leases
и ещё не наступивший `cleanup_after` исключаются. Поэтому накопленная очистка
не задерживает новые uploads. При непрерывной очереди обработки очистка может
отставать: контролировать её возраст и размер карантина; lifecycle остаётся
дополнительной страховкой для исходников.

Sandbox принимает ровно один документ за жизнь контейнера и затем обязательно
перезапускается. В локальном Compose процесс живёт минимум 11 секунд с момента
старта, чтобы сбросить restart backoff; второй документ во время ожидания не
принимается. Теоретический потолок одного sandbox — менее 5,5 документа/минуту
(3600/11 ≈ 327 в час), фактически ниже из-за запуска, AV/CDR и I/O. Изображения
тоже используют этот sandbox. Worker выполняет один job последовательно и делает
паузу 1 секунду между шагами; обработка файла требует нескольких шагов. Это не
SLA для файла или оценка производительности production. Для большей нагрузки
нужен пул изолированных одноразовых sandbox (в Kubernetes — отдельные pods),
с сохранением принципа «один документ на контейнер», лимитов и сетевой изоляции.

ZIP: не более 4096 записей/512 МиБ распаковки/100:1 сжатия, XML до 8 МиБ
и глубины 128; ZIP64 и комментарии запрещены. PDF — до 100 страниц, изображения
до 40 млн пикселей суммарно и 10 000 пикселей по каждой стороне; результат до 100 МиБ. Сигнатуры ClamAV старше
48 часов, timeout, неоднозначный ответ или неполная обработка не дают READY.

Собирать только конечные метрики: очередь/возраст состояний, истёкшие leases,
ошибки зависимостей, задержка репликации, возраст AV-сигнатур/сертификатов,
остаток места, размер карантина. SQL `files.audit` хранит переходы состояний;
JSON control audit — метод, код результата, случайный `file_id`, workload/pod и
`tenant_id`, `subject_id`, `session_id` проверенного Auth-принципала. Идентификаторы
записываются после успешной проверки подписи и текущей сессии, включая последующий
отказ по scope/owner; при неуспешной аутентификации поля принципала отсутствуют.
`session_id` — корреляционный идентификатор Auth, не cookie или bearer token.
Состав этих служебных идентификаторов закреплён в ADR-0015; доступ к аудиту ограничен
операторами безопасности, он не предназначен для пользовательской аналитики.

Worker пишет JSON в stderr: `file_id`, исходное `state`, конечный `stage` и
`error_class` (`unavailable`, `rejected`, `conflict`, `not_found`,
`deadline_exceeded`, `canceled`, `invalid`, `limit`, `unknown`). Ошибка Claim не
имеет `file_id`, поскольку job ещё не выбран. Пустая очередь не логируется;
отсутствующий объект и потерянный CAS после Claim логируются. Класс и этап
позволяют отличить отказ CDR/AV от storage/DB без вывода сырой ошибки зависимости.
Не добавлять request/response bodies, headers, URL, JWT и имена файлов в telemetry.

Ротация: сначала добавить доверенный CA/новые IAM credentials, выдать новые
короткоживущие сертификаты, пересоздать процессы, проверить smoke и отозвать
старые полномочия. Старые версии KMS key сохранять до переноса и проверки всех
объектов/backup; уничтожение ключа делает данные невосстановимыми.

Инцидент: выключить публичные флаги, отозвать capability principals, остановить
приём; сохранить метаданные/аудит без экспорта пользовательских файлов. После
исправления восстановить проверку SHA/AV/CDR и обе clean-копии. READY не
выставляется вручную. При потере DC сначала оградить старую БД от записей,
подтвердить WAL синхронной реплики, затем переключать writer и control routing;
самостоятельное ослабление `remote_apply` запрещено.

Откат: сначала выключить оба browser-флага, дождаться 60 секунд жизни URL,
отключить control, затем worker. Сохранить buckets, DB и KMS. Down-миграция
удаляет метаданные и допускается только для пустого тестового окружения;
для эксплуатируемого контура нужен перенос данных. Не удалять volumes для
обычного отката к предыдущему binary.

Воспроизводимые проверки и ограничения приёмки — [отчёт MM-43](../../../docs/testing/files-data-plane.md).
