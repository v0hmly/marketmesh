# Локальный кабинет с настоящими сервисами

> Постоянный dev использует общий [корневой стенд](../dev/README.md) и `task dev:up`.
> Описанные ниже отдельные Compose — интеграционные фикстуры и legacy cleanup;
> прямой persistent `up` отключён. Не создавайте второй набор баз для разработки.

Окружение MM-64 запускает storefront, Auth, User и пару gateway на одном HTTPS
origin. Регистрация создаёт профиль через настоящий outbox Auth → NATS JetStream →
consumer User. SQL-заготовок профилей и подмены Auth нет. Текущий состав профиля
и адресной книги, а также тема оформления согласованы и описаны в
[спецификации кабинета](../../docs/product/account.md).

В MM-93 включён `/account/id`: личные поля сохраняются в User через те же
`GetMe`/`UpdateMe` и общую версию профиля. При запуске применяется добавочная
миграция User `000005_identity`. Браузерный E2E проверяет Unicode, сохранение после
повторного входа, конфликт вкладок, изоляцию владельцев, сохранение полей старым
редактором и потерю ответа после выполненной записи.

## Запуск

Нужны Docker Compose, Go и Task из [требований проекта](../../README.md#требования).
Node, pnpm и Chromium для полного E2E устанавливаются внутри закреплённых Docker
образов. Из корня репозитория:

```sh
task account:up
task account:status
task account:probe
task account:down
```

Адрес кабинета — `https://localhost:8443`. Опубликован только loopback-порт
frontdoor; PostgreSQL, Redis, NATS и служебные порты приложений не публикуются.
Для другого порта или одновременной работы из нескольких worktree задайте
`ACCOUNT_LOCAL_PORT` и уникальный `ACCOUNT_LOCAL_PROJECT` с префиксом
`marketmesh-account-` перед каждой командой:

```sh
ACCOUNT_LOCAL_PROJECT=marketmesh-account-demo ACCOUNT_LOCAL_PORT=18443 task account:up
ACCOUNT_LOCAL_PROJECT=marketmesh-account-demo ACCOUNT_LOCAL_PORT=18443 task account:down
```

Скрипт выводит путь к публичному сертификату локального CA. Он не добавляет CA в
системное хранилище доверия. Для ручного просмотра нужен браузер с отдельно
настроенным доверием к этому CA; воспроизводимые браузерные проверки ниже
создают такое доверие только внутри одноразового контейнера Chromium. Проверить
HTTPS без изменения хранилища доверия позволяет встроенная в `up` Go-проверка
с выданным CA.

`up` сохраняет пароли, сертификаты и данные при повторном запуске, применяет новые
миграции и проверяет checksum уже применённых. `down` удаляет контейнеры и сети,
сохраняя тома с базами и событиями. Для удаления данных **выбранного локального
проекта** предназначена отдельная команда:

```sh
task account:reset
```

Сертификаты действуют семь дней. Истёкшее окружение и изменение порта требуют
явного `reset`, затем `up`; автоматической ротации ключей поверх существующих
сессий нет. Состояние хранится в игнорируемом `.state/<project>/`, родительский
каталог имеет права `0700`. Не копируйте его в коммиты, отчёты или Docker context.

`probe` выполняет только чтение и выводит агрегированные счётчики. После
обработки регистрации `registration_outbox_pending`, `events_pending` и
`events_ack_pending` должны вернуться к нулю; `registration_inbox_applied` и
`profiles` увеличиваются. Кратковременное отставание счётчиков нормально. Если
профиль остаётся в подготовке, сначала проверьте `status`: Auth публикует outbox,
NATS хранит событие, а User применяет inbox. Идентификаторы пользователей,
содержимое событий и строки профиля команда не выводит.

Безопасная остановка — `down`. При неудачном обновлении оставьте тома и каталог
состояния на месте, вернитесь к предыдущей проверенной task-ветке и повторите
`up`. Миграции автоматически назад не откатываются: несовместимое изменение
checksum останавливает запуск. Для одноразовых тестовых данных можно явно
выбрать `reset` и создать окружение заново.

## Опциональная локальная аналитика

Для подключения storefront к локальному Rybbit выполните
[инструкцию MM-75](../rybbit/README.md#подключение-кабинета). По умолчанию
аналитика выключена. Включённый контур использует отдельный сайт и сеть Rybbit,
а браузер обращается только к своему HTTPS origin.


## Реальные браузерные проверки

```sh
task account:test
```

Команда создаёт отдельный временный Compose-проект, затем удаляет его контейнеры
и тома. Если порт 8443 занят ручным окружением, задайте свободный
`ACCOUNT_LOCAL_PORT`, например `18444`. Результаты остаются в каталоге состояния
тестового проекта; runtime-состояние исключено из Git и Docker build context.

Проверка состоит из двух фаз. Сначала consumer User выключен: браузер регистрирует
аккаунт, входит и получает настоящий `PROFILE_NOT_READY`. Затем consumer
запускается, обрабатывает событие и тот же аккаунт получает профиль. Проверяются:

- изменение и сохранение профиля после перезагрузки;
- сохранение темы после повторного входа, смена владельца и независимость версий
  профиля, адресной книги и настроек;
- конфликт версий между вкладками с сохранением черновика;
- изоляция двух владельцев и отказ анонимному клиенту;
- HttpOnly/Secure/SameSite cookies, отсутствие секретов в browser storage;
- отзыв текущей и всех сессий, включая повтор старых cookies;
- честное сообщение о неподтверждённом выходе при потере сети;
- адресная книга: CRUD, основной адрес, CAS, чужие ID и сохранение после входа;
- реально сохранённый адрес и реально отозванная сессия с потерянным ответом;
- полный Unicode-снимок из 20 адресов больше 64 КиБ и отказ при 21-м добавлении;
- проверка доверенного HTTPS и отказ сертификату постороннего CA в Chromium и Node.

TLS-проверка Chromium включена. В контейнер браузера монтируется только публичный
CA. Trace, видео, HAR и снимки сессий отключены; reporter печатает статические
названия тестов и строки проверок, без значений паролей и cookies. Быстрые
компонентные и браузерные проверки с подменой ответов остаются отдельным набором,
описанным в [storefront](../../frontend/apps/storefront/README.md).

## Границы локального окружения

Frontdoor отдаёт собранную статику и проксирует только публичные Auth/User RPC по
проверяемому HTTPS в gateway-in. Он не использует forwarded-заголовки как
подтверждение защищённого соединения. Gateway-out открывает обратный mTLS-туннель
из внутренней сети в DMZ. Auth и User используют общий PostgreSQL primary и одну synchronous replica,
отдельные логические базы `auth` и `user`, роли `auth_rw/auth_ro` и
`user_rw/user_ro` и служебные сертификаты. Доступ каждой роли к чужой базе,
`postgres` и `template1` запрещён. `synchronous_commit=remote_apply` гарантирует
видимость завершённой записи через RO; при недоступной реплике запись обоих
сервисов ждёт её восстановления. NATS использует mTLS и раздельные
права publisher, consumer и provisioner; административный ключ не монтируется
в приложения. Приватный ключ CA существует только в памяти генератора.

Compose запускает два экземпляра gateway-in с разными идентификаторами процесса:
это требование готовности существующего пула gateway-out. В этой фиксированной
тестовой топологии генератор задаёт `TUNNEL_PERIODIC_REDISCOVERY_ENABLED=false`:
периодическое закрытие рабочего туннеля могло оставлять выбранный frontdoor
экземпляр без маршрута и давать 503. Флаг допустим только с `ENVIRONMENT=test`;
восстановление после сетевых ошибок и устранение дублирующих соединений сохранены.
Autoscaling и rolling deployment этот контур не проверяет; доступность при
перераспределении в production отслеживается отдельно в MM-70. Проверка `up` ждёт
готовности gateway-out и общей пары PostgreSQL, затем проверяет публичный путь.
TLS использует ECDSA P-256, совместимый с NSS Chromium; ключи подписания
assertion Auth остаются Ed25519 по действующему контракту.

Это локальная конфигурация: PostgreSQL и Redis работают без TLS внутри закрытой
Compose-сети; для Redis причина явно передаётся в конфигурации Auth. Генератор,
provisioner и часть контейнеров работают с правами root внутри контейнера, а
диагностические секреты доступны владельцу Docker. Окружение не предназначено
для внешнего размещения или production. Отдельный Files overlay для аватаров описан ниже; покупки MM-55 сюда не входят.


Адресная книга MM-68 включается в этом локальном контуре на User и обоих шлюзах;
storefront собирается с `VITE_ACCOUNT_ADDRESSES_ENABLED=true`. Provision применяет
добавочную миграцию `000003_addresses`; профиль, созданный раньше, получает пустую
книгу с версией 1. Auth выдаёт отдельные scopes чтения/записи адресов. Для внешнего
окружения эти флаги по умолчанию выключены; порядок поставки описан в
[Gateway In](../../backend/services/gateway-in/README.md#адресная-книга-mm-68).

Браузерный runner доверяет публичному CA контура и в Chromium NSS, и в Node
(`NODE_EXTRA_CA_CERTS`) для пересылки реальных запросов в тестах потери ответа.
Проверка TLS остаётся включённой; чужой self-signed сертификат отклоняется.

Настройки MM-69 также включены локально: `USER_SETTINGS_ENABLED`,
`USER_SETTINGS_BROWSER_ENABLED` на обоих шлюзах и
`VITE_ACCOUNT_SETTINGS_ENABLED=true` при сборке storefront. Provision применяет
`000004_settings`, Auth выдаёт отдельные settings scopes; для старых и новых
профилей исходная тема — системная. Frontdoor обслуживает `/account/settings`
и только два новых публичных RPC, не закрытые Browser-конверты.

## Переход на общий PostgreSQL (MM-74)

Новый контур содержит ровно два PostgreSQL-контейнера: `postgres-primary` и
`postgres-replica`. Миграции и ledger остаются отдельными в каждой логической базе.
Реплика использует physical slot `account_sync`; автоматического failover нет.
Базовый контур `infra/compose` и изолированные сервисные integration fixtures
сохраняют свою отдельную область применения.

Старый `ready.json` без версии топологии 2 отклоняется **до запуска контейнеров**.
Команда `up` не переносит и не удаляет старые базы и секреты. Чтобы сохранить старое
окружение, остановите его прежней версией `account:down` и запустите новую версию
под другим `ACCOUNT_LOCAL_PROJECT` и свободным портом. Старые volumes и `.state`
останутся для возврата к предыдущему commit. Если данные одноразовые, можно явно
выполнить `account:reset` для старого проекта, затем `account:up`.

Автоматический перенос данных из двух физических кластеров не выполняется.
Для ценных локальных данных сначала сохраните дампы обеих баз и старый `.state`;
не восстанавливайте роли старого кластера поверх новых ролей. Откат без переноса —
старый commit, исходный проект и его сохранённые volumes/секреты.

`account:test` проверяет обе реальные RW/RO пары, отказ подключения к чужим базам,
read-only endpoint, немедленное чтение записи и сохранение маркеров после restart
обоих PostgreSQL. Проверка создаёт служебные таблицы только в одноразовом тестовом
проекте и удаляет их перед продолжением браузерных сценариев.

## Почта и сценарии Auth (MM-90)

Стенд включает локальный Mailpit без внешнего relay. UI/API доступны только на
`http://127.0.0.1:8025` (`ACCOUNT_MAILPIT_PORT` меняет порт); SMTP `mailpit:1025`
доступен внутри контейнерной сети и не публикуется на хосте. Приложение — прежний
`https://localhost:8443` (`ACCOUNT_LOCAL_PORT`). Регистрация теперь принимает почту
и пароль с согласованными требованиями; перед первым входом нужно подтвердить
почту по письму. Настройки входа доступны на `/account/security`.

Генератор создаёт постоянный `auth/mail.key` с правами 0600 и включает новый
runtime Auth. Topology version — 3: старое состояние версии 2 автоматически не
перезаписывается. Для проверки создайте отдельный `ACCOUNT_LOCAL_PROJECT`, либо
явно сбросьте только ненужные одноразовые данные. Не удаляйте старый стенд для
обхода проверки конфигурации.

`local.sh test` использует отдельный проект и случайный loopback-порт Mailpit;
браузер читает только его синтетические письма через отдельную сеть. Проверяются
подтверждение почты, включение кода, повторная выдача после ошибок, смена почты,
сброс пароля, отзыв старых cookie, одноразовые ссылки и доступность форм.
Коды/ссылки остаются в памяти теста, reporter выводит только статические имена и
места проверок. SMTP-параметры и план отката — в
[описании Auth email](../../docs/security/auth-email.md).


## Аватары с настоящим Files (MM-65)

Нужен уже запущенный собственный стенд [files-local](../files-local/README.md).
Команда подключает account-local к его закрытым сетям и данным, применяет User
миграции и собирает storefront с аватаром. Mailpit остаётся локальным.

```sh
# Значения по умолчанию Files: marketmesh-files-local и .cache/files-local.
python3 infra/account-local/files.py up
# HTTPS localhost:18443; Mailpit localhost:18025.
python3 infra/account-local/files.py test
python3 infra/account-local/files.py down
```

Для существующего именованного стенда передайте `FILES_LOCAL_PROJECT` и
`FILES_LOCAL_STATE` (абсолютный каталог внутри `.cache`), а для аккаунта —
`ACCOUNT_LOCAL_PROJECT`, `ACCOUNT_LOCAL_PORT`, `ACCOUNT_MAILPIT_PORT`. Скрипт
отказывает чужим owner-marker и Compose resources. Повторный `up` сохраняет
PKI, почтовый ключ, базы, storage и KMS; `down` не удаляет volumes.
`files.py renew` согласованно останавливает только свой account overlay,
перевыпускает workload PKI и запускает всех его потребителей. Срок сертификатов
короткий; истёкший PKI отклоняется с указанием этой команды. Отдельная PKI самого
Files/storage обновляется его `local.py renew`, без удаления данных.

CA публичного приложения и Files объединены в указанном командой файле
`browser/combined-ca.pem`. Browser runner доверяет им только внутри собственного
контейнера (NSS/Node); системный trust store хоста не меняется. При ручном запуске
браузера требуется доверие обоим локальным CA. Прямые HTTPS storage endpoints —
localhost:18343–18345; frontdoor не проксирует файловые байты.

`files.py test` создаёт отдельный account-проект, выполняет pending и core фазы,
проверяет реальную загрузку/AV/CDR/привязку/замену/удаление, чужого владельца,
неготовый файл, CAS и потерю ответа. После проверки удаляет только созданные
account resources; внешний Files сохраняется. Тест добавляет только постоянный
origin `https://frontdoor:8443`, сохраняя ранее настроенные точные CORS origins
работающих кабинетов. Список ограничен 32 origins; wildcard отклоняется. Синтетические файлы проходят
обычный lifecycle Files. Учтите [лимит одноразового sandbox](../../backend/services/files/README.md):
один документ на контейнер и обязательный перезапуск, минимум 11 секунд.
Границы доверия, параметры поставки и ограничения — в [MM-65](../../docs/security/account-avatar.md).
