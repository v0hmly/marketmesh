# Storefront: дизайн-система

Уточняет корневой AGENTS.md для `frontend/apps/storefront`. Полная спецификация —
[docs/design/design-system](../../../docs/design/design-system/README.md); единственный источник значений — `docs/design/design-system/tokens.json`.
Исполняемые общие стили — `frontend/packages/design-system/style.css`;
`src/style.css` только подключает пакет. Любой новый экран или компонент должен
собираться из описанных ниже токенов и паттернов, а не из новых hex-значений и размеров.

## Токены

- Цвета берутся только из CSS-переменных общей дизайн-системы (`--page`, `--paper`,
  `--ink`, `--muted`, `--line`, `--green`, `--link`, `--brand-accent`, `--focus`, `--danger`,
  `--button-*`, `--input-*`, `--error-*`, `--success-*`, `--reconcile-*`, `--pending`,
  `--low-stock`).
  Литеральные hex в компонентах запрещены.
- Новый цвет добавляется только в `tokens.json` с light/dark. `task design:generate`
  создаёт CSS для документации и пакета, включая явные темы и системный media query.
  Сгенерированные CSS игнорируются Git и вручную не меняются. Совместимые старые
  имена находятся в `packages/design-system/aliases.css`, без второй палитры.
- Палитра — тёплый графит на бумаге с одним охряным акцентом (MM-124). Графит — текст и
  основное действие (`--green` — историческое имя `action-primary`, сейчас графит). Охра —
  `--link` (`text-link`: ссылки, подписи вторичных и текстовых кнопок, рамка поля в фокусе,
  выбранный пункт), `--focus` и `--brand-accent`. Вне этих двух гамм только статусы:
  `--danger` (кирпичный) для ошибок валидации и неудачных запросов и приглушённый зелёный
  `--success-*`. `--brand-accent` декоративный (около 2.4:1 на светлом фоне) и не обозначает
  состояние. Состояние reconcile (конфликт черновика и сервера) — не ошибка, оно использует
  `--reconcile-*`.
- Контраст: текст ≥ 4.5:1, нетекстовые элементы ≥ 3:1 в обеих темах. Границы полей и
  вторичных кнопок (`--input-border`, `--button-border`) и точка ожидания (`--pending`) равны
  токенам `border-control` и `status-pending` (MM-97); декоративные линии — `--line`.

## Типографика

- Шрифты: Inter (текст, UI), Georgia (только `h1` и инициалы аватара). Других семейств нет.
- `h1` — Georgia 400, `clamp(2.8rem, 5.3vw, 4.9rem)`, `letter-spacing: -0.065em`; на телефоне 3.1rem.
  В кабинете покупателя `h1` — название раздела 2.6rem (`.account-heading`, на телефоне 2.2rem);
  тот же масштаб у заглавия главной витрины (`.storefront-heading`), без eyebrow.
- `h2` — Inter 600, 1.55rem (в карточках 1.35rem); `h3` — 1.05rem; `h4` — 0.9rem.
- Шкала размеров: 0.65 / 0.73 / 0.8 / 0.875 / 1 / 1.15 / 1.55 rem. Новые значения между
  шагами не вводятся.
- `.eyebrow` — 0.64rem, вес 650, `letter-spacing: 0.16em`, заглавные, `--muted`.
- `.lede` и `.field-help` — `line-height: 1.8` и `1.6`; основной текст — 1.55.
- Цифры в счётчиках и метаданных — `font-variant-numeric: tabular-nums`.

## Сетка и отступы

- Контейнер `.site-wrap` 1320px; поля 64px (≥1000), 35px (720–1000), 22px (<720).
- Брейкпоинты только три: `max-width: 720px`, `max-width: 1000px`, `min-width: 1400px`.
- Шкала отступов: 4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 56 / 64 px. Значения вроде 11, 13,
  17, 27, 33 px в новом коде не используются.
- Двухколоночные сетки (`.profile-layout`, `.auth-layout`) схлопываются в одну колонку на 720px.

## Форма и тени

- Радиусы: 8px кнопки и поля, 10px панели, 18px карточки, pill для бейджей, 50% для аватара.
- Одна тень — `0 5px 18px var(--shadow)` только у `.card`. Другие тени не добавляются.
- Границы 1px `--line` (у контролов — `--input-border`); 3px — только фокус.

## Компоненты

Использовать существующие классы, не создавать параллельные:

- Кнопки: `.button.primary` (основное действие, с `<span aria-hidden="true">↗</span>` если
  действие куда-то ведёт), `.button.secondary`, `.button.text-button` (низкорисковые действия
  вроде выхода), модификатор `.wide`. Высота 45px, компактная 42px только в `.session-controls`
  (общий выход вне кабинета покупателя). Основная кнопка на экране одна; остальные действия —
  `.secondary` или `.text-button`.
- Поле: `.field` → `label` (или `.label-line` с `.field-count`) → контрол → `.field-help` →
  `.field-error`. Ошибка не заменяет подсказку, а добавляется под ней. Контролы 48px.
- Карточки: `.card` + `.identity-card` (тонированная, с `.initials`), `.profile-card` /
  `.auth-card` (форма), `.state-card` (одно сообщение по центру, при ожидании — `.loading-dot`).
- Уведомления: `.notice.error` с `role="alert"`, `.notice.success` с `role="status"`.
  Inline, без тостов. Конфликт сервера и черновика — `.reconcile-panel` со своими действиями,
  и только он: подтверждение необратимого действия — диалог `ConfirmDialog` (компонент Dialog).
- Список: `select` внутри `.select-wrap` (шеврон на CSS).
- Шапка страницы: `.eyebrow` → `h1` → `.lede`, справа `.section-number` (скрыт на телефоне).
  В кабинете покупателя — `.account-heading`: `h1` с названием раздела и `.lede`, без eyebrow и
  номера.

## Доступность

- Фокус двухцветный: `outline: 3px solid var(--focus); outline-offset: 3px;
  box-shadow: 0 0 0 3px var(--focus-inner)` на `:focus-visible`; не убирать. Охра снаружи на
  светлой теме даёт около 2.2:1, контраст держит тёмное внутреннее кольцо.
- Формы: `novalidate`, `aria-invalid`, `aria-describedby` со списком id ошибки, подсказки и
  счётчика; `aria-busy` во время отправки.
- Декоративные глифы (↗ ↳ ✳) всегда `aria-hidden="true"`.
- Единственный transition — 150ms у границы поля; `prefers-reduced-motion` отключает его.
- Browser-тесты прогоняют axe на реальных формах; новый экран обязан их проходить.

## Голос и тексты

- Русский, «вы», без восклицательных знаков.
- Заголовки — законченные предложения с точкой: «Рады вас видеть.», «Начнём знакомство.».
- Действия — инфинитив с объектом: «Сохранить изменения». Во время выполнения — «мы» в
  настоящем времени с многоточием: «Сохраняем…», «Проверяем…».
- Ошибка отвечает на три вопроса подряд: что случилось · что мы сделали · что делать вам.
  Без извинений.
- Подсказка формулирует правило до того, как пользователь его нарушит: «Без пробелов. Регистр не важен.»
- Глиф ↳ зарезервирован за строкой приватности «Данные этого раздела доступны только вам.».

## Экраны авторизации

Прототипы экранов и писем — [docs/design/prototypes](../../../docs/design/prototypes/README.md).
Оттуда берутся структура, тексты, состояния и набор ошибок; разметка собирается на классах
storefront по правилам выше.

- Логин — почта. Пароль — от 8 до 64 символов, плюс строчная и заглавная латинские буквы,
  цифра и спецсимвол (согласовано с MM-72 и bcrypt на стороне Auth).
- Требования к паролю показываются списком с отметками «выполнено» и появляются только после
  того, как пользователь начал вводить пароль. Отдельного счётчика длины нет: длина — такое же
  условие списка, как остальные. `.field-count` остаётся только там, где у поля есть жёсткий
  максимум, например название магазина.
- Проверка — по отправке формы (`novalidate`), не по нажатию клавиши. После первой попытки
  ошибки пересчитываются на каждый ввод, чтобы исчезать по мере исправления.
- При неверной паре почта-пароль экран не уточняет, какое поле неверно; существование учётной
  записи не раскрывается ни при входе, ни при восстановлении.
- После пяти неудачных попыток вход блокируется на время; после трёх неверных кодов код
  перевыпускается. Оба состояния — `.notice.error` с тем, что произошло и что делать.
- Подтверждение входа кодом на почту обязательно для покупателей и продавцов и не отключается
  (решение владельца от 23.09.2026). Серверная часть — MM-98; пока она не сделана, Auth ещё
  допускает отключение, но новых переключателей в UI не добавлять. Резервных кодов нет (MM-91
  отменена). Сотрудники входят через корпоративный SSO без пароля портала. Поле кода — шесть
  цифр, `inputmode="numeric"`, `autocomplete="one-time-code"`, нецифры отсекаются при вводе.
- Внутренний портал доступен только из корпоративной сети. Запрос извне — отдельное состояние
  экрана с объяснением про VPN, а не общая ошибка сервера.

## Кабинет покупателя

Прототипы — `AccountOrders`, `AccountFavorites`, `AccountReviews`, `BuyerAddresses`,
`MarketMeshId`; правило меню — `components/Navigation.md` дизайн-системы.

- Каркас — layout-маршрут `/account` (`AccountLayout.vue`): слева панель 268px (230px на
  720–1000px, над содержимым ниже 720px), справа экран раздела. Меню не вставляется в экраны.
- Панель видна только владельцу сессии. В ней сверху вниз: вертикальное меню разделов, список
  «Тема оформления» (при `VITE_ACCOUNT_SETTINGS_ENABLED`) и текстовая кнопка «Выйти из
  аккаунта». Тема сохраняется сама: через 500 мс после последнего выбора (стрелки на закрытом
  списке не отправляют промежуточные темы) или сразу при уходе фокуса, с CAS по версии настроек
  из account/settings; конфликт и неизвестный исход перечитываются, запись не повторяется.
- Разделы: «Заказы», «Избранное», «Отзывы» (со счётчиками), «Адреса доставки», «MarketMesh ID» —
  каждый за своим флагом. Без флага ID вместо него стоит «Вход и безопасность»
  (`/account/security`). Новые пункты добавляются только как разделы; тема и выход — не пункты.
- `/account` ведёт на первый доступный раздел (заказы, иначе ID); `/account/settings` — в кабинет;
  `/account/security` — в MarketMesh ID к разделу «Вход и безопасность» (`#security`).
- MarketMesh ID содержит почту для входа строкой «Личных данных» с отметкой подтверждения,
  разделы «Вход и безопасность» (почта, пароль, код входа) и «Сеансы и устройства»
  (`AccountSecurity.vue`). «Выйти на всех устройствах» закрывает и текущий сеанс — подпись
  говорит об этом прямо. Удаление аккаунта не выводится до MM-92.
- Поле «О себе» в интерфейсе не показывается; при сохранении ID значение User передаётся как
  прочитано.
- На экране MarketMesh ID открыта одна форма и видна одна основная кнопка. Пока открыта правка
  личных данных, вход и сеансы не меняются: смена пароля, кода и выход на всех устройствах
  закрывают сеанс и стёрли бы черновик. Пока открыта форма входа или ждёт код, правку не начать.
  Загрузка аватара — вторичная кнопка.
- Пока профиль готовится (`profilePending`), разделы показывают `ProfilePending.vue` с проверкой
  готовности, а не приглашение ко входу: вход уже выполнен.

## Страницы ссылок из писем

Маршруты `/account/security/verify`, `reset`, `change_email`, `cancel_email`; прототипы —
`Security*.dc.html`.

- Открытие ссылки ничего не меняет: действие выполняется кнопкой, и кнопка называет действие
  («Подтвердить почту», «Сохранить пароль»), а не «Подтвердить действие».
- Подводка говорит, что будет после нажатия (например, что закроются все сеансы), а не как
  устроена ссылка.
- Кнопка без формы стоит прямо под подводкой, без карточки вокруг. Голый `<fieldset>` без
  сброса стилей даёт серую рамку браузера — сбрасывать `border`, `padding`, `margin`,
  `min-width`.
- Подтверждение регистрации (MM-101) в браузере регистрации сразу открывает кабинет
  через сессию shell; пароль и второй код не спрашиваются. В другом браузере ссылка
  лишь подтверждает почту и предлагает обычный вход.
- После успеха остальных действий основной становится «Войти ↗»; ссылка «Перейти ко входу» до подтверждения не
  нужна.
- Истёкшая или использованная ссылка — одно состояние с запросом нового письма (для почты и
  пароля); ответ на запрос нейтральный. Неизвестный исход не выдаётся за успех или ошибку.

## Витрина

Прототипы — `Home`, `Product`, `Shop`; главная для гостя — `GuestHome` в проекте Claude Design.
Главная (MM-125) — модуль `src/modules/catalog`, маршрут `/` (без флага, MM-132: стендов пока
нет, прятать её не от кого). Пока нет API каталога, корзины и
обратной связи (эпики MM-52 … MM-55), данные берутся из `catalog/sample-data.ts`, а корзина
хранится в `localStorage` этого браузера и общая для всех, кто в нём входит; избранное и
подписки на пополнение живут только в памяти страницы и сбрасываются при смене сеанса.

- Шапка витрины — именованный вид `header` маршрута с `meta.storefront`: shell выводит его
  вместо своей навигации и не показывает общую панель выхода. Поиск, корзина и вход живут там.
- Действия, которым нужен аккаунт (избранное, «Сообщить о пополнении», оформление заказа,
  «Напишите нам»), у гостя открывают `ConfirmDialog` «Вход в MarketMesh ID» с причиной, а не
  уводят со страницы молча.

- Лента без персонализации: у каждого раздела понятное основание (новые партии, мастерские с
  покупками, пополнения из избранного). Приветствия и пояснений об устройстве ленты нет.
- Остаток партии показывается всегда («В партии 8 из 10», «Осталось 2 из 12»,
  «В партии 7 из 7»,
  «Партия распродана») вместе с датой партии; распроданная позиция приглушена и предлагает
  «Сообщить о пополнении». `status-danger` не используется ни для распроданности, ни для
  избранного.
- Бирка партии на плитке (MM-126, MM-133): под фото строка остатка (никогда не обрезается),
  под ней шкала партии, под шкалой отдельной подписью дата — «партия от 29 сентября».
  Масса шкалы следует смыслу (MM-129): у обычной партии тонкая 2px цветом камня (`--muted`),
  у заканчивающейся — 4px охрой (`--low-stock`): два изделия или меньше и не больше трети
  партии (`lowStock` в `catalog/store.ts`), чтобы «2 из 3» не горело всегда. У полной партии
  шкалы нет — ей нечего показывать. Шкала `aria-hidden` и только дублирует подпись; малый
  остаток (≤ 2) подписан полужирным. Обе заливки держат 3:1 к карточке и к дорожке в обеих
  темах; `--brand-accent` для шкалы не годится (2.4:1).
- Слоты плитки выровнены по ряду (MM-133): плитка — `subgrid` на 8 рядов сетки (фото,
  остаток, шкала, дата, цена, название, мастерская, действие), все слоты — прямые потомки,
  высота слота — по самой длинной карточке ряда. Фото — одна пропорция (`aspect-ratio: 1`).
  Название — до 2 строк (на телефоне до 3) с неразрывными пробелами у единиц (`keepUnits`);
  мастерская — только имя, одна строка с многоточием, «Мастерская» — для скринридера.
- Количество в карточке изделия ограничено остатком выбранного варианта; основная кнопка одна.
- В подвале — форма «Напишите нам» без поля почты (ответ идёт на почту MarketMesh ID) и с
  вторичной кнопкой отправки.

## Письма авторизации

Пятнадцать шаблонов (`Email*.dc.html`) лежат там же: подтверждение почты, код входа, вход с
нового устройства, сброс и смена пароля, смена почты двумя письмами, блокировка входа,
закрытие сессий, включение и отключение подтверждения входа, резервные коды, решение по заявке
продавца, приглашение сотруднику, удаление аккаунта. Письма о включении и отключении
подтверждения входа и о резервных кодах не используются: код входа обязателен, резервных кодов
нет (MM-98, MM-91).

- В прототипах письма свёрстаны флексами и переменными; в рассылку уходят таблицы с
  захардкоженными hex — CSS-переменные в почтовых клиентах не работают. Georgia в заголовках
  безопасна, Inter подменится на Segoe UI или Arial. Тёмная тема требует `color-scheme` и
  собственного медиазапроса.
- Одно письмо — одно действие. Кнопка-ссылка дублируется текстовой ссылкой, срок действия
  ссылки указывается всегда.
- В письмах безопасности основная кнопка — защитное действие («Это не я — сменить пароль»).
  Кнопки «это я» нет: она ничего не делает и приучает нажимать на всё в письмах.
- Код входа отправляется письмом. Резервных кодов нет.
- Значения в квадратных скобках — заглушки, их заменяют реальными до вёрстки.

## Знак проекта

Монограмма: строчная «m» Georgia в круге `--action-primary`. В интерфейсе — круг, для фавиконки
и ярлыка приложения — квадратная плитка с радиусами из токенов, на тёмном — светлая плитка с
графитовой буквой. Образцы — `docs/design/prototypes/Mark.dc.html`.

Класс `.brand-mark` находится в `packages/design-system/style.css` и в `components/bundle.css` (MM-82): коробка 35×35 в
`border-box`, без `letter-spacing`, `padding-right` и `overflow`, буква центрируется флексом и
`translateY(-0.06em)`; разметка — `<span class="brand-mark"><span>m</span></span>`. Слой-поправка
из `prototypes/tokens-vars.css` удалён; новые патчи под знак не вводятся.
