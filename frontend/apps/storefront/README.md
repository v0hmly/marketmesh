# Storefront: аккаунт покупателя

Vue-приложение кабинета MM-50. Использует реальные публичные Connect-контракты Auth
и User; встроенных demo-аккаунтов или подмены API в приложении нет. Текущая форма
профиля показывает согласованные `display_name`/`bio`. MM-68 добавляет адресную
книгу с несколькими адресами; сохранение темы относится к MM-69.

## Проверки и сборка

Из корня репозитория, с версиями Node/pnpm из корневого `package.json`:

```sh
pnpm install --frozen-lockfile
task frontend:verify
pnpm --filter @marketmesh/storefront test:browser
```

`build` включает TypeScript и выдаёт статический `dist`. `lint` проверяет запрет
HTML-вставок, прямого импорта внутренних API и связей между продуктовыми модулями.
Компонентные integration-тесты могут собирать настоящий shell router; это исключение
не распространяется на production imports.

Browser-тесты требуют Chromium для закреплённой версии Playwright
(`pnpm --filter @marketmesh/storefront exec playwright install chromium`) и OpenSSL.
Они создают и удаляют временный TLS-сертификат, запускают Vite только на loopback
и используют типизированную подмену сетевых ответов **только в тестах**. Проверяются
реальные формы, Web Locks между вкладками, доступность axe, мобильная вёрстка и
очистка данных. Полный Auth → событие регистрации → User → UI E2E запускается
отдельно командой `task account:test`, описанной в
[руководстве локального кабинета](../../../infra/account-local/README.md).
В быстрых тестах с подменой ответов доверие к сертификату backend не проверяется.

## Запуск с API

Публичные RPC и статические файлы приложения должны обслуживаться на одном
HTTPS origin. API-клиент обращается к `/auth.v1.AuthService/*` и
`/user.v1.UserService/*` на текущем origin; cross-origin base URL не настраивается.
Статический сервер должен возвращать `index.html` для `/login`, `/register` и
`/account` и `/account/addresses`, не перехватывая RPC-маршруты. Персональные ответы остаются `no-store`.

Для Vite можно передать `STOREFRONT_TLS_CERT` и `STOREFRONT_TLS_KEY` с путями к
локальной паре сертификата/ключа и выполнить
`pnpm --filter @marketmesh/storefront dev`. Одного Vite недостаточно для входа:
нужен same-origin frontdoor к настоящему gateway-in. Воспроизводимая полная
конфигурация запускается через `task account:up`; инструкции по локальному CA
приведены в руководстве выше. HTTP показывает понятный экран необходимости
защищённого соединения.

## Границы и сессия

- `shell/session` хранит статус, непрозрачный идентификатор текущего владельца в
  памяти и поколение сессии; профиль и черновики принадлежат `modules/account`.
- `shared/api` — единственная граница с generated API. Внутренний Auth assertion
  и gateway transport не экспортируются браузерным фасадом. `PROFILE_NOT_READY`
  распознаётся только по стандартному protobuf `ErrorInfo`, не тексту ошибки.
- Session-changing RPC выполняются под общим exclusive Web Lock, операции профиля
  — под shared lock с проверкой владельца/поколения. Обычный refresh сохраняет
  поколение и черновик. Смена аккаунта или выход очищает персональное состояние.
- В localStorage сохраняется лишь журнал операции: случайные generation/operationId,
  kind и phase. Токены, subject, пароль и профиль туда не попадают. BroadcastChannel
  только уведомляет вкладки; решения принимаются по журналу и ответам API под lock.
- Незавершённый или неоднозначный refresh не повторяется. При отсутствии Web Locks
  или доступного coordination storage вход закрывается с объяснением; небезопасного
  fallback через временную localStorage-блокировку нет.
- UpdateMe не повторяется автоматически. После конфликта или неизвестного исхода
  можно прочитать сохранённый профиль и явно выбрать актуальные данные или черновик.
- Сетевой сбой выхода не объявляется успешным серверным отзывом. HttpOnly cookie
  удаляет Auth; JavaScript не пытается прочитать или заменить его.

Продуктовые решения и отложенные зависимости описаны в
[модели кабинета](../../../docs/product/account.md).

## Адресная книга MM-68

Раздел `/account/addresses` и ссылка на него доступны при сборке с
`VITE_ACCOUNT_ADDRESSES_ENABLED=true`. В API должны быть включены адресные флаги
User и обоих шлюзов, описанные в [Gateway In](../../../services/gateway-in/README.md#адресная-книга-mm-68).
По умолчанию frontend-флаг выключен; локальный полный контур включает его явно.

Книга сохраняет до 20 адресов с отдельной версией. Первое добавление в пустую книгу
назначает основной адрес; удаление основного оставляет остальные без автоматического
выбора замены. Изменения не повторяются автоматически. После конфликта или
неизвестного исхода нужно перечитать снимок и явно выбрать актуальную книгу или
свой черновик. После неизвестного создания интерфейс предупреждает о возможной
уже сохранённой записи; исчезнувший редактируемый адрес не превращается в новый.

Книга и черновики живут только в памяти модуля. Все операции проходят session
shared lock и проверку владельца/поколения до и после сети. Смена владельца очищает
данные синхронно; запоздалый ответ их не восстанавливает. Вход и регистрация ждут
первоначальную проверку сессии, чтобы смена поколения не стирала уже начатый ввод.

### Оформление аккаунта

`VITE_ACCOUNT_SETTINGS_ENABLED=true` включает раздел `/account/settings` и загрузку
настроек в shell. Флаг независим от `VITE_ACCOUNT_ADDRESSES_ENABLED`; по умолчанию
оба выключены. Настройки читаются через публичный `GetSettings`, сохраняются через
`UpdateSettings` с отдельной `expected_version`. Значения `system`, `light`, `dark`
переходят в явные protobuf enum; неизвестное значение или некорректная идентичность
ответа отклоняются.

Shell применяет только подтверждённую сервером тему на всех страницах. При выборе
radio оформление ещё не меняется: нужно сохранить. `system` реагирует на настройку
устройства. После входа и перезагрузки shell снова читает настройки; ошибка чтения
не блокирует профиль и оставляет ручной повтор. Выход, смена владельца и неопределённая
сессия немедленно сбрасывают предпочтение в `system`. Поздний ответ прежнего владельца
или более старая версия не возвращает старую тему. Настройки и предпочтения не
попадают в Web Storage, URL и BroadcastChannel.

Конфликт CAS и неизвестный результат записи сохраняют выбор, блокируют повторную
отправку и требуют перечитать настройки, затем явно принять их либо оставить свой
выбор для сохранения. Версии профиля, адресной книги и настроек независимы. Проверки
включают межвкладочный конфликт, потерю ответа действительно выполненной записи,
смену владельца, доступность светлой/тёмной темы и восстановление после нового входа.
