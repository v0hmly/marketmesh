# Инструкции для работы с MarketMesh

Этот файл действует для всего репозитория. Более вложенный AGENTS.md может уточнять правила только для своей директории, но не должен ослаблять требования безопасности, Taskboard, Git Flow и CI.

Проектная документация, задачи Taskboard и описания pull request ведутся на русском языке. Имена в коде, идентификаторы протоколов, имена веток и другие технические обозначения остаются на английском.

## Taskboard — источник задач

Проект в Taskboard называется MarketMesh и использует префикс MM.

- Любое изменение кода, документации или инфраструктуры начинается с конкретной задачи Taskboard.
- Для ответа на вопрос, чтения или диагностики без изменений создавать задачу не требуется.
- Перед созданием задачи нужно проверить, нет ли уже подходящей, чтобы не создавать дубликат.
- Если пользователь запросил изменение, а задачи нет, агент создаёт конкретную задачу в проекте MarketMesh до начала редактирования и сообщает её ключ.
- При начале работы задача переводится из todo в in_progress.
- Одна ветка обслуживает одну задачу. Несвязанные изменения разносятся по разным задачам и веткам.
- Ключ задачи обязателен в имени ветки и заголовке pull request.
- В описании pull request указываются задача, цель, существенные решения, способ проверки, риски и план отката, если изменение влияет на развёртывание или данные.
- Задача переводится в done только после слияния в целевую интеграционную ветку и успешного прохождения обязательного CI. Одних локальных изменений или открытого pull request недостаточно.
- Если работа заблокирована, задача остаётся in_progress, а причина блокировки сообщается пользователю.

Taskboard использует иерархию «проект → задача → подзадача». Не следует создавать umbrella-задачи вместо проекта. Большая техническая задача может иметь подзадачи и ветку epic.

## Постоянные ветки и окружения

### main

main — единственное имя основной ветки; имя master не используется.

main содержит код, одобренный для production. Фактическое состояние production определяется последним успешно развёрнутым защищённым тегом и неизменяемыми digest артефактов, а не только HEAD ветки: deployment может завершиться неуспешно.

Прямые push, force-push и удаление main запрещены.

### dev

dev — интеграционная ветка следующего релиза и источник обычных задач. Успешное изменение dev автоматически развёртывается в dev-окружение.

dev может опережать production, но обязана оставаться собираемой и проходить обязательные проверки. Незавершённые возможности, которые нужно интегрировать рано, скрываются feature flags.

Прямые push, force-push и удаление dev запрещены.

## Имена и назначение веток

Ключ вида MM-26 является ключом задачи Taskboard. После ключа рекомендуется добавлять короткое описание в lower-kebab-case.

| Вид | Формат | Базовая ветка | Целевая ветка |
| --- | --- | --- | --- |
| Обычное изменение | feat/MM-26 или feat/MM-26-short-description | dev; для подзадачи активного epic — соответствующий epic | Та же интеграционная ветка, от которой начата работа |
| Исправление | fix/MM-27 или fix/MM-27-short-description | По умолчанию dev; для release-блокера — release; для дефекта epic — epic | Ветка, содержащая дефект |
| Большая интеграционная работа | epic/MM-40 или epic/MM-40-short-description | dev | dev |
| Исправление production | hotfix/MM-42 или hotfix/MM-42-short-description | Последний успешно развёрнутый тег, commit которого находится в main | main с последующим переносом вперёд |
| Релиз-кандидат | release/v1.2.0 | dev | main и затем обратно в dev |

feat применяется к запланированным изменениям продукта, документации и инфраструктуры, если они не являются исправлением, hotfix или epic.

В имени ветки запрещены пробелы, произвольные идентификаторы без ключа задачи и несколько ключей несвязанных задач. Исключение — release/vX.Y.Z: релизная ветка называется по версии, а связанная релизная задача указывается в pull request.

## Обычная задача

1. Найти или создать задачу Taskboard и перевести её в in_progress.
2. Определить целевую интеграционную ветку: обычно dev, а для подзадачи epic — соответствующую epic-ветку.
3. Обновить локальную целевую ветку без переписывания её общей истории.
4. Создать feat/MM-* или fix/MM-* от целевой ветки.
5. Выполнить только относящиеся к задаче изменения и добавить проверки.
6. Открыть pull request обратно в исходную интеграционную ветку.
7. Получить обязательное ревью и успешный CI.
8. Слить небольшую task-ветку методом squash merge и удалить её.
9. Перевести задачу в done после подтверждённого слияния.

Локальную task-ветку допустимо rebase на свежую целевую ветку до публикации или пока ей не пользуются другие. Общие epic, release, dev и main переписывать запрещено.

## Epic

epic — временная интеграционная ветка большой работы, а не релизная ветка и не постоянная замена dev. Она используется как исключение, когда изменение нельзя безопасно разбить и скрыть feature flags.

- epic/MM-* создаётся от актуальной dev.
- Каждая часть epic имеет отдельную задачу и создаётся от epic как feat/MM-* или fix/MM-*.
- Части вливаются обратно в epic через pull request и CI.
- Изменения dev регулярно вливаются в epic merge-коммитом. Общую epic-ветку нельзя rebase или force-push.
- Когда epic готов целиком, он вливается в dev через pull request с merge commit, без squash и rebase.
- После успешного слияния epic-ветка удаляется.
- Релиз всегда создаётся от dev, а не напрямую от epic.

Если epic живёт долго, владелец обязан регулярно проверять совместимость с dev, размер расхождения и возможность дальнейшего разбиения.

## Release и preprod

1. Для согласованной версии создаётся релизная задача Taskboard.
2. release/vX.Y.Z создаётся от проверенной dev.
3. Каждый успешный HEAD release/vX.Y.Z развёртывается в preprod как неизменяемый кандидат с зафиксированными digest артефактов.
4. После создания release действует feature freeze: допускаются только release-блокирующие исправления, миграционные корректировки, документация релиза и изменения поставки.
5. Исправление создаётся как fix/MM-* от release/vX.Y.Z и возвращается pull request в ту же release-ветку.
6. Исправления release регулярно переносятся в dev merge-коммитом, чтобы не потеряться в следующем релизе.
7. Принятый release/vX.Y.Z вливается в main через pull request с merge commit, без squash и rebase.
8. На полученном commit main создаётся защищённый аннотированный тег vX.Y.Z, от которого один раз собираются неизменяемые релизные артефакты.
9. Артефакты тега с зафиксированными digest проходят финальную проверку в preprod.
10. Production deployment продвигает без повторной сборки те же digest, которые прошли финальную проверку в preprod.
11. После успешного deployment main или release синхронизируется с dev merge-коммитом, релизная задача закрывается, а release-ветка удаляется.

Тег не «принадлежит ветке»: он указывает на конкретный commit. Поэтому production-тег создаётся только на commit, уже находящемся в main.

Если deployment неуспешен, фактическим production остаётся предыдущий успешно развёрнутый тег. Существующий тег нельзя перемещать или переиспользовать. Инфраструктурную ошибку можно исправить повторным продвижением того же артефакта; изменение кода требует новой patch-версии.

До отдельного ADR тег vX.Y.Z версионирует платформу MarketMesh целиком. Независимое версионирование отдельных микросервисов или frontend-модулей должно быть принято отдельным решением.

## Hotfix

hotfix применяется только к дефекту, который присутствует в production и не может ждать обычного release.

1. Создать или найти задачу и перевести её в in_progress.
2. Создать hotfix/MM-* от последнего успешно развёрнутого тега. Его commit обязан находиться в истории main.
3. Открыть pull request в main, выполнить полный обязательный CI и ревью.
4. После слияния создать новую patch-версию vX.Y.Z и продвинуть проверенный неизменяемый артефакт в production.
5. Влить main в dev, а также в активные release и epic, если исправляемый дефект присутствует в них.
6. Удалить hotfix-ветку и закрыть задачу после успешного deployment и переноса исправления вперёд.

Hotfix не создаётся от dev: dev может содержать изменения будущего релиза.

## Pull request и стратегия слияния

- feat и fix сливаются в свою интеграционную ветку через squash merge.
- epic и release сливаются через merge commit; squash и rebase merge для них запрещены.
- Перенос main, release и dev друг в друга выполняется merge-коммитом.
- Pull request не должен содержать изменения других задач, случайное форматирование или не относящееся обновление зависимостей.
- Автор обязан обновить ветку относительно целевой и повторить проверки после разрешения конфликтов.
- Для критичных директорий применяются CODEOWNERS и дополнительное ревью владельца.
- Draft pull request можно использовать для раннего обсуждения, но он не даёт права на merge или deployment.

## Защита веток, тегов и окружений

Для main, dev, release/* и epic/* должны быть настроены GitHub rulesets:

- изменения только через pull request;
- минимум одно независимое одобрение;
- сброс устаревшего одобрения после существенного обновления;
- обязательное разрешение обсуждений;
- обязательные status checks от доверенных GitHub Apps;
- запрет force-push и удаления;
- ограниченный bypass только для документированного аварийного процесса.

Теги v* защищены от изменения и удаления. Их создаёт только релизная автоматизация или явно уполномоченная роль.

Окружения разделены:

| Окружение | Источник | Требование |
| --- | --- | --- |
| dev | dev | Успешный CI |
| preprod | release/vX.Y.Z; перед production — защищённый vX.Y.Z | Успешный CI и неизменяемые артефакты |
| production | защищённый vX.Y.Z | Ручное или политическое подтверждение, один deployment одновременно, promotion проверенных digest |

Секреты каждого окружения изолированы. Код pull request из недоверенной ветки не получает production-секреты и не публикует артефакты.

## Минимальные проверки CI

Обязательный набор постепенно расширяется вместе с кодовой базой, но соответствующая проверка не может быть пропущена только потому, что она ещё не настроена как required check.

- проверка форматирования и отсутствие незакоммиченных результатов генерации;
- lint для затронутых Go и frontend-проектов;
- модульные тесты;
- Go-тесты с race detector там, где это поддерживается;
- интеграционные и контрактные тесты для изменённых границ;
- проверка protobuf и обратной совместимости схем;
- сборка изменённых приложений и контейнеров без публикации из pull request;
- сканирование известных уязвимостей, секретов и контейнеров;
- проверка миграций и совместимости последовательного развёртывания;
- проверка ссылок и структуры документации.

Пропуск обязательной проверки оформляется явным, ограниченным по времени исключением с причиной и владельцем; молчаливое отключение запрещено.

## Неизменяемые правила

- Нельзя разрабатывать новую задачу непосредственно в main, dev, release или epic.
- Нельзя выпускать production из commit, отсутствующего в main.
- Нельзя добавлять новую функциональность в уже созданный release.
- Нельзя перемещать опубликованный тег или заменять связанный с ним артефакт.
- Нельзя считать HEAD main доказательством фактически работающей версии без успешной записи deployment.
- Нельзя завершать задачу Taskboard до merge и обязательных проверок.
- Нельзя объединять в одной ветке несколько несвязанных задач ради удобства.
- Исключение из процесса требует явного согласования с пользователем и фиксации причины.
